**Суммарно FN: 879**, из них ~399 неизбежны (unparseable), ~400 — устранимый артефакт вайтлиста.

### 5.4 Новый источник FN: ndots и search domain expansion

**Что происходит.** В Kubernetes по умолчанию `ndots=5` в resolv.conf. Когда под запрашивает `exfil.attack.test` (3 компонента < 5), DNS-клиент **сначала пробует suffixed варианты**:

1. `exfil.attack.test.attack.svc.cluster.local` → NXDOMAIN
2. `exfil.attack.test.svc.cluster.local` → NXDOMAIN
3. `exfil.attack.test.cluster.local` → NXDOMAIN
4. `exfil.attack.test.lan` → (search suffix ноды) → forwarded/NXDOMAIN
5. `exfil.attack.test` → фактический запрос к туннелю

Шаги 1–3 попадают под `CLUSTER_DNS_SUFFIXES` whitelist → **detector возвращает score=0 → FN**.

В логах это видно как по 80 событий на каждый вариант:
```
*.exfil.attack.test.attack.svc.cluster.local  80
*.exfil.attack.test.svc.cluster.local         80
*.exfil.attack.test.cluster.local             80
```

**Масштаб:** ~400 FN из 879 (~45%) — из-за слишком широкого вайтлиста.

**Почему вайтлист ошибается.** Текущая проверка:
```python
if any(domain.endswith(s) for s in config.CLUSTER_DNS_SUFFIXES):
    return False, None, [], 0
```
Она не различает `kubernetes.default.svc.cluster.local` (легитимный сервис) и `exfil.attack.test.svc.cluster.local` (атака с ndots-суффиксом). Обоим отказывает.

**Правильная проверка** должна убедиться, что домен _действительно_ является k8s-сервисом: он должен разрешаться как `<service>.<namespace>.svc.cluster.local`, где `<service>` и `<namespace>` — реальные имена без посторонних меток.

### 5.6 Выводы по Phase C (Прогон 2)

1. **Direct access BPF критически улучшил recall:** 0.55 → 0.856 в сырых метриках. Это основной результат прогона 2.

2. **Реальный FPR остаётся крайне низким:** ~0.017% при 465k событий. Baseline почти не задет.

3. **Главный источник FN сменился:** с `<unparseable>` (было 1719) на ndots/search expansion (новый, 400 событий). Это устранимо фиксом вайтлиста.

4. **`<unparseable>` сократился с ~1719 до 399** — это прямой эффект direct access. Остаток — вероятно IPv6, требует добавки поддержки IPv6 в BPF.

## 5b. Результаты Phase C: Прогон 3 — с новыми фиксами

### 5b.1 Контекст

После Прогона 2 были выявлены три проблемы:
1. **MANY_SUBDOMAINS на `cluster.local`** — все K8s сервисы группируются под base_domain=`cluster.local`, вызывая ~42K FP
2. **Проверка кодировки только в parts[0]** — пропускала chunked exfil типа `1.base64data.exfil.test`
3. **Порог кодировки > 20 символов** — пропускал 20-символьные base64 данные

### 5b.2 Сырые метрики (Прогон 3, до фиксов)

**GT by pod (namespace):**

| Threshold | TP | FN | FP | TN | Precision | Recall | FPR |
|-----------|------|-----|-------|--------|-----------|--------|-----|
| 2 | 5720 | 399 | 49049 | 469061 | 0.1044 | 0.9348 | 9.467% |

**GT by domain (`--gt-by-domain --attack-domain attack.test`):**

| Threshold | TP | FN | FP | TN | Precision | Recall | F1 | FPR |
|-----------|-------|-----|-------|--------|-----------|--------|-------|------|
| 2 | 11837 | 0 | 42932 | 469460 | 0.2161 | **1.0000** | 0.3554 | 8.379% |
| **3** | **11477** | **360** | **20** | **512372** | **0.9983** | **0.9696** | **0.9837** | **0.004%** |

### 5b.3 Анализ проблем

**Проблема 1: MANY_SUBDOMAINS на cluster.local (~42K FP)**

Детектор считает `base_domain = '.'.join(parts[-2:])` → для всего K8s DNS это `cluster.local`. Уникальные "subdomains":
- `kube-dns.svc` (от `kube-dns.svc.cluster.local`)
- `pod-0.headless-svc.default.svc` (от headless pod)
- `_dns._udp.kube-dns.kube-system.svc` (SRV records)
- ...и т.д.

Результат: >50 уникальных subdomains → `MANY_SUBDOMAINS(50)` → score=2 → FP на легитимном трафике.

**Проблема 2: Кодировка проверялась только в parts[0]**

Exfil-домен `1.ldF90b2tlbl8xMjM0NQo.exfil.attack.test.lan`:
- `parts[0]` = `1` (chunk number) — не срабатывает
- `parts[1]` = `ldF90b2tlbl8xMjM0NQo` (base64 данные, 20 символов) — не проверялся!

**Проблема 3: Порог > 20 вместо >= 16**

`ldF90b2tlbl8xMjM0NQo` = 20 символов. Порог `len > 20` требовал 21+. Результат: BASE64_SUBDOMAIN не срабатывал.

### 5b.4 Внесённые исправления

| Файл | Исправление |
|------|-------------|
| `config.py` | Добавлен `CLUSTER_BASE_DOMAINS = {"cluster.local", ...}` |
| `exfil.py` | Пропуск `MANY_SUBDOMAINS` для `base_domain in CLUSTER_BASE_DOMAINS` |
| `exfil.py` | Проверка кодировки во **всех** `parts[:-2]`, не только `parts[0]` |
| `exfil.py` | Порог кодировки снижен до `>= 16` символов |

| Метрика | До | После (ожид.) | Изменение |
|---------|----|--------------| ----------|
| FP (GT by pod, th=2) | 49049 | ~78 | −99.8% |
| FN (GT by domain, th=3) | 360 | ~0 | −100% |
| Precision | 0.1044 | ~0.99 | +90% |

## 7. Технические артефакты (детально)

### 7.1 eBPF: прямой доступ — unparseable снизились, но не исчезли

- **Факт (Прогон 1):** ~2175 FN в Phase C из-за `<unparseable>`.
- **Факт (Прогон 2):** После перехода на direct access (ctx->data/data_end, одна bounds check) `<unparseable>` упали до **399**. Recall вырос с 0.55 до 0.856.
- **Причина оставшихся 399:** Вероятно IPv6 (offset 28 под IPv4, DNS на IPv6 читается с мусорного места). Диагностика: поле `ip_version` в событии + `payload_sample_hex` при DEBUG_UNPARSEABLE=1.
- **Следующий шаг:** добавить ветку IPv6 в BPF (offset 48) — устранит большую часть из 399.

### 7.2 CLUSTER_DNS_SUFFIXES whitelist — слишком широкий

- **Факт:** 400 FN в Прогоне 2 из-за ndots/search domain expansion (см. раздел 5.4).
- **Причина:** Белый список `*.cluster.local` убирает легитимные сервисы (корректно) и атакующие домены с ndots-суффиксами (некорректно).
- **Исправление:** Проверять, что домен соответствует паттерну `<service>.<namespace>.svc.cluster.local` с реальными именами (1-2 метки без внешних доменов внутри), а не просто оканчивается на `.cluster.local`.

Пример:
```python
# Текущий (слишком широкий):
domain.endswith(".svc.cluster.local")
# → "exfil.attack.test.svc.cluster.local" тоже проходит → FN

# Правильный (проверяет структуру):
import re
K8S_SVC_RE = re.compile(r'^[a-z0-9\-]+\.[a-z0-9\-]+\.svc\.cluster\.local$')
K8S_SVC_RE.match(domain)
# → "kubernetes.default.svc.cluster.local" ✓
# → "exfil.attack.test.svc.cluster.local" ✗ (3 метки до svc, не 2)
```

### 7.3 Методология ground truth в analyze.py

- **Факт:** События от подов в `attack` / `attack-server` → attack; от `kube-system` (CoreDNS) → legit. Туннельный трафик проходит через CoreDNS → алерты на CoreDNS считаются FP.
- **Следствие:** Precision занижена (0.477 vs реальная ~0.99). FPR завышен (1.24% vs реальные 0.017%).
- **Правильное решение:** разметка по домену (`*.attack.test` → attack) или исключение CoreDNS из подсчёта. Реализуемо в analyze.py за 2-3 ч (`--gt-by-domain`).

### 7.4 In-cluster серверы усиливают CoreDNS artifact

- Серверы туннелей внутри кластера (namespace `attack-server`). CoreDNS форвардит `*.attack.test` → ClusterIP → каждый DNS-обмен виден как: клиент → CoreDNS → сервер (три источника событий). Это утраивает "FP" на CoreDNS-транзите.
