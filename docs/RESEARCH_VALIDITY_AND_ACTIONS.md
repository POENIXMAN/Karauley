# Критическая оценка двух объяснений и что делать

Два резюме из твоего ресерча — насколько они совпадают с фактами и что из этого реально делать.

---

## 1. Оценка по пунктам

### «Главная боль — iov_iter, ты угадываешь смещения»

**Частично верно.**  
У нас в логах бывает **ptr_primary_probe_ok** и **send_ptr_ok** — то есть указатель из iov_iter мы **получаем**, и 2-байтовая проба по нему проходит. Значит на **этих** ядрах/путях layout (24/16) не сломан: проблема не в «data_ptr всегда мусор».  
Но на других ядрах или при других iter_type смещения могут быть не те → **ptr_null** / **probe_read_fail**. Тезис «ручные смещения опасны, layout плавает» — **верный**. Debug-карты (ptr_ok/ptr_null, union_primary/fallback, iter_type) как раз показывают, где именно ломается: часть отказов точно может быть из-за iov_iter.

**Итог:** iov_iter — реальный источник части проблем; не единственный там, где уже есть ptr_ok + kernel_ok и мусор в payload.

---

### «K8s ничего дополнительно не режет»

**Спорно.**  
У нас типичная картина: **user_ok=0**, **kernel_ok>0**, контент в `dns_data` не DNS (нули, посторонние байты). Это можно объяснить и так:

- «K8s не режет» — ограничения только от ядра (layout, lifetime, verifier).
- Либо **user namespace** контейнера всё же мешает `bpf_probe_read_user` (мы так и писали в WHY_HOST_WORKS_CONTAINER_NOT).

Третье объяснение из второго ответа (см. ниже) — **paging / atomic context** — снимает противоречие: user read может падать не из-за «K8s запретил», а из-за того, что в контексте kprobe нельзя делать page fault по user-адресу. Тогда и на голой машине в «неудачном» контексте будет то же самое.  
**Итог:** утверждение «K8s сам по себе не вводит доп. запретов» может быть верным; тогда причина — layout ядра + контекст выполнения (paging/atomic), а не политика контейнеров.

---

### «Memory context trap: paged out / atomic context»

**Очень правдоподобно.**  
В kprobe мы в контексте ядра, часто «атомарном». Чтение user-памяти через `bpf_probe_read_user` может потребовать подкачки страницы (page fault). Если в этом контексте fault не разрешён, хелпер отдаёт ошибку → мы идём в `bpf_probe_read_kernel` по тому же (user) VA → ядро не падает, но отдаёт не буфер процесса, а что-то другое (нулевая страница и т.д.) → мусор в payload.  
Это **ровно** совпадает с наблюдаемым: user read не проходит, kernel read «успешен», но контент неправильный. Объяснение «не user namespace, а контекст/пагинация» — сильное и его стоит считать основным кандидатом наряду с layout.

---

### «Stack limit: struct dns_event ~320 bytes, 512 limit»

**Верно.**  
`struct dns_event`: 4+4+16+8+4+4+4+2+2+1+1+2+2+2+2+8+2+256 ≈ **320 bytes**. Плюс на стеке: `struct iov_iter iter` (десятки байт), локальные переменные, выравнивание. Итого мы **близко к 512** или уже заходим в зону риска в части путей (TCP, recv и т.д.). Верификатор может режеть или поведение станет нестабильным.  
**Итог:** перенос события в per-CPU буфер (map) — не «на всякий случай», а обоснованная мера.

---

### «Pivot: sys_enter_sendto / udp_send_skb»

- **sys_enter_sendto:** буфер задаётся одним указателем (нет iov_iter). Если проблема только в layout iov_iter — там может заработать. Если проблема в контексте (paging/atomic) — user-указатель там тоже может не читаться. Минимальный тест (10 строк) имеет смысл как **диагностика**: заработало там и не в kprobe → сильный намёк на контекст.
- **udp_send_skb (или позже по стеку):** payload уже в **skb** в ядре. Чтение через `bpf_probe_read_kernel` из skb — корректно, без user-буфера и без iov_iter. Это **архитектурно правильный** выход: хук там, где данные уже в ядре.

## 2. Сводка: что из исследований тянет

| Тезис | Вердикт |
|-------|--------|
| iov_iter и ручные смещения — источник части проблем | Да; у нас не «всегда мусор», но на других ядрах/путях — да. |
| K8s сам по себе не режет eBPF-доступ к памяти | Возможно; тогда виноваты layout + контекст (paging/atomic). |
| Paged out / atomic context → probe_read_user fail | Очень правдоподобно, хорошо объясняет user_ok=0 и мусор после kernel read. |
| Stack 512, event ~320 — опасно | Да; нужен вынос события из стека. |
| Проверить layout по BTF на ноде | Полезно и дёшево. |
| Пробовать sys_enter_sendto как тест | Полезная диагностика. |
| Пivot на skb (udp_send_skb и т.п.) | Правильное направление для стабильного решения. |

## 3. Что делать (без прикрас)

### Сделать в первую очередь

1. **Вынести событие со стека**  
   Per-CPU map под буфер `dns_event`, в kprobe только заполняешь его и делаешь `perf_submit` из map (или копируешь в буфер из map). Убирает риск лимита стека и капризов верификатора.

2. **Проверить layout iov_iter по BTF на ноде**  
   На проблемной ноде:
   ```bash
   bpftool btf dump file /sys/kernel/btf/vmlinux format c | grep -A 30 "struct iov_iter {"
   ```
   Сравнить смещения с нашими константами (0, 8, 16, 24). Если отличаются — поправить или вынести в конфиг под ядро.

3. **Минимальный тест sys_enter_sendto**  
   Отдельная крошечная программа: tracepoint или kprobe на `sys_enter_sendto`, прочитать буфер по указателю из аргументов (без iov_iter). Если там payload читается, а в udp_sendmsg — нет, это аргумент в пользу контекста (atomic/paging), а не только layout.

### Если хочешь стабильно читать payload в любом окружении

4. **Перейти на хук по skb**  
   Точка входа, где DNS payload уже в ядре (например после копирования в skb): тип программы (e.g. BPF_PROG_TYPE_SCHED_CLS или другой, в зависимости от точки), парсинг skb (сетевые заголовки, UDP, payload). Никакого iov_iter и user-буфера — только `bpf_probe_read_kernel` по ядерной памяти. Работа заметно сложнее (парсинг пакета, привязка к интерфейсу/очереди), но это путь к «всегда читаем правильные байты».

5. **CoreDNS как источник доменов**  
   Уже описано в COREDNS_AS_DNS_SOURCE: логи CoreDNS дают домен, клиента, тип. Никакого eBPF-чтения user-памяти, нет зависимости от ядра и layout. Для детекции по доменам этого достаточно; eBPF тогда опционален (метаданные, частота и т.д.).

### Чего не ждать

- Настройки «прав» или «режима пода» в K8s сами по себе не починят чтение user-буфера из kprobe, если причина — контекст выполнения или layout.
- Один универсальный набор смещений iov_iter для «любого» ядра в кластере — ненадёжен; либо BTF/версия ядра, либо уход с iov_iter (skb / CoreDNS).

---

## 4. Итог одной фразой

Оба ответа в целом по делу: и iov_iter с ручными смещениями, и контекст (paging/atomic), и лимит стека — реальные факторы. «K8s не режет» может быть верно, если считать главной причиной контекст ядра, а не политику контейнеров. Дальше имеет смысл: снять риск стека, проверить layout по BTF, провести тест sendto; для долгосрочного решения — либо хук по skb (payload в ядре), либо домены из CoreDNS без чтения user-памяти в eBPF.
