# Алгоритмы детекции DNS-туннелей

Документ описывает текущие алгоритмы детекции по коду в `dns_tunnel_monitor/`. Источник истины: реализация в `detectors/`, `dns_parsing.py`, `config.py` и `bpf/dns_cgroup.bpf.c`.

---

## 1. Что именно анализирует система

Система перехватывает DNS-пакеты на уровне `cgroup_skb`, копирует первые `128` байт полезной нагрузки DNS в userspace, пытается извлечь:

- доменное имя;
- тип DNS-записи;
- число ответов;
- направление `query/response`;
- `cgroup_id`, `client_pod`, `process`.

Дальше событие прогоняется через три группы эвристик:

1. `C2Detector` для каналов управления через DNS.
2. `ExfiltrationDetector` для выноса данных через поддомены.
3. `IPOverDNSDetector` для туннелей типа `iodine`.

Результаты объединяются в `TunnelDetector`, который считает взвешенный `score`. Если `score >= 2`, событие помечается как `suspicious`.

---

## 2. Общая схема принятия решения

### 2.1 Предобработка

До запуска эвристик система:

- отбрасывает события без распознанного домена (`<unparseable>`);
- не анализирует домены, которые распознаны как легитимные cluster-internal имена Kubernetes через `is_legitimate_cluster_dns()`;
- выделяет `base_domain` как две последние метки домена.

### 2.2 Веса причин

| Причина | Вес |
|---------|-----|
| `C2_BEACON` | 3 |
| `C2_TXT_REQUEST` | 1 |
| `HIGH_ENTROPY` | 2 |
| `LONG_DOMAIN` | 1 |
| `HIGH_DIGIT_RATIO` | 1 |
| `HEX_SUBDOMAIN` | 2 |
| `BASE64_SUBDOMAIN` | 2 |
| `MANY_SUBDOMAINS` | 2 |
| `HIGH_RATE` | 3 |
| `NULL_RECORD` | 2 |
| `MANY_ANSWERS` | 2 |

### 2.3 Правило алерта

- итоговый `score` равен сумме весов сработавших причин;
- текущий порог: `SCORE_THRESHOLD = 2`;
- итоговый `threat_type` формируется как комбинация `C2`, `EXFIL`, `TUNNEL`.

Это значит, что один слабый признак не всегда вызывает алерт, а комбинация нескольких умеренных сигналов уже может сработать.

## 3. Детектор C2

Файл: `dns_tunnel_monitor/detectors/c2.py`

### 3.1 Какая атака покрывается

Детектор рассчитан на:

- beaconing к управляющему домену;
- использование TXT-запросов как канала управления.

Типичный пример: `dnscat2` и другие DNS C2-клиенты с периодическим polling.

### 3.2 Алгоритм 1: регулярность beacon

Идея: C2-клиент часто делает периодические DNS-запросы к одному базовому домену.

Как работает:

- ключ состояния: `(cgroup_id, base_domain)`;
- хранятся только timestamps для `query`, а не для `response`;
- максимум хранится `20` последних timestamps;
- для срабатывания нужно минимум `5` наблюдений;
- считается средний интервал и коэффициент вариации `CV = std / mean`;
- причина `C2_BEACON(...)` добавляется, если:
  - `CV < 0.15`;
  - средний интервал `> 5` секунд.

Почему это полезно:

- улавливает регулярные опросы C2;
- почти не зависит от конкретного имени домена.

Ограничения:

- не ловит очень редкий трафик, если за окно не набралось `5` запросов;
- не ловит нерегулярный beacon с jitter;
- работает по `base_domain`, который сейчас считается как две последние метки и не учитывает Public Suffix List;
- хранит максимум `10_000` ключей, после чего старые вытесняются по LRU.

### 3.3 Алгоритм 2: подозрительные TXT-запросы

Идея: TXT-запросы часто легитимны для SPF, DKIM, DMARC, ACME и похожих сценариев, но могут использоваться и как C2-канал.

Как работает:

- проверяется `dns_type == 16`;
- домен сравнивается с built-in whitelist и опциональным файлом `TXT_WHITELIST_FILE`;
- если домен не попал в доверенные префиксы, суффиксы и точные совпадения, добавляется причина `C2_TXT_REQUEST`.

Почему это полезно:

- хорошо выделяет atypical TXT-запросы к внешним доменам;
- особенно эффективно на инструментах вроде `dnscat2`.

Ограничения:

- результат зависит от полноты whitelist;
- редкие, но легитимные TXT-сценарии могут давать FP;
- атакующий может использовать не TXT, а другой тип записи.

## 4. Детектор эксфильтрации

Файл: `dns_tunnel_monitor/detectors/exfil.py`

### 4.1 Какая атака покрывается

Детектор ориентирован на:

- передачу данных в поддоменах;
- chunked exfiltration;
- кодирование полезной нагрузки через hex/base64-подобные строки.

Типичный пример: `DNSExfiltrator`, часть сценариев `dnscat2`, кастомные скрипты с base64/hex в subdomain.

### 4.2 Алгоритм 1: высокая энтропия

Идея: домены с закодированными или случайными данными имеют более равномерное распределение символов.

Как работает:

- из домена убираются точки;
- считается энтропия Шеннона;
- если `entropy > 4.1`, добавляется `HIGH_ENTROPY(x.xx)`.

Почему это полезно:

- улавливает base64/hex/случайные куски данных даже без знания конкретного инструмента.

Ограничения:

- некоторые легитимные домены CDN, telemetry и API тоже могут иметь повышенную энтропию;
- атака с короткими или словарными метками может не пройти порог.

### 4.3 Алгоритм 2: длинное имя

Идея: при выносе данных домен часто становится длинным.

Как работает:

- если `len(domain) > 60`, добавляется `LONG_DOMAIN(n)`.

Ограничения:

- захватывается только первые `128` байт DNS payload, поэтому длинное имя может быть обрезано или не распарсено полностью;
- это вспомогательный, а не основной признак.

### 4.4 Алгоритм 3: высокая доля цифр

Идея: кодированные метки нередко содержат много цифр.

Как работает:

- считается доля цифр в домене без точек;
- если `digit_ratio > 0.3`, добавляется `HIGH_DIGIT_RATIO`.

Ограничения:

- сам по себе это слабый сигнал;
- некоторые легитимные сервисные домены тоже могут содержать много цифр.

### 4.5 Алгоритм 4: кодирование в поддоменах

Идея: полезная нагрузка часто кодируется в одном или нескольких поддоменах.

Как работает:

- перебираются все части `parts[:-2]`, то есть все поддомены до `base_domain`;
- если длина поддомена `>= 16`:
  - строка из `[0-9a-fA-F]+` даёт `HEX_SUBDOMAIN`;
  - строка из `[A-Za-z0-9+/=]+` даёт `BASE64_SUBDOMAIN`.

Почему это полезно:

- это один из самых сильных признаков для DNS exfil;
- после исправления проверяются все поддомены, а не только первый.

Ограничения:

- URL-safe base64 (`-` и `_`) отдельно не учитывается;
- hex является частным случаем более общего символьного шума, но проверяется первым;
- короткие чанки могут не пройти порог длины.

### 4.6 Алгоритм 5: много уникальных поддоменов

Идея: эксфильтрация часто использует один и тот же `base_domain`, но генерирует много уникальных поддоменов.

Как работает:

- для каждого `base_domain` хранится список уникальных поддоменов;
- максимум в памяти хранится `50` уникальных значений;
- если число уникальных поддоменов становится больше `40`, добавляется `MANY_SUBDOMAINS(n)`;
- для `cluster.local`, `svc.cluster.local`, `pod.cluster.local` этот признак отключён, чтобы не ловить штатный Kubernetes DNS.

Почему это полезно:

- один из лучших признаков для chunked exfiltration.

Ограничения:

- счётчик ограничен `50` значениями и работает как FIFO;
- легитимные шумные домены тоже могут вести себя похоже;
- базовый домен снова вычисляется только как две последние метки.

## 5. Детектор IP-over-DNS

Файл: `dns_tunnel_monitor/detectors/ip_over_dns.py`

### 5.1 Какая атака покрывается

Детектор рассчитан на DNS-туннели, которые используют DNS как транспорт для постоянного обмена данными.

Типичный пример: `iodine`.

### 5.2 Алгоритм 1: высокий rate

Идея: IP-over-DNS создаёт плотный поток DNS-событий к одному и тому же домену.

Как работает:

- ключ состояния: `(cgroup_id, base_domain)`;
- окно по времени: `10` секунд;
- если с начала окна прошло больше `1` секунды, считается `rate = count / elapsed_sec`;
- если `rate > 150 req/s`, добавляется `HIGH_RATE`.

Почему это полезно:

- хорошо ловит быстрые туннели с непрерывной передачей данных.

Ограничения:

- low-and-slow туннели этот порог могут не пересечь;
- длительное окно агрегации не реализовано;
- хранится максимум `10_000` ключей по LRU.

### 5.3 Алгоритм 2: NULL-записи

Идея: тип `NULL` редко встречается в обычном трафике, но характерен для `iodine`.

Как работает:

- если `dns_type == 10`, добавляется `NULL_RECORD(iodine)`.

Ограничения:

- это очень сильный, но узкоспециализированный сигнал;
- другие туннели могут обходиться без `NULL`.

### 5.4 Алгоритм 3: много ответов

Идея: туннель может пытаться упаковать много данных в один DNS response.

Как работает:

- если `dns_answers > 15`, добавляется `MANY_ANSWERS(n)`.

Ограничения:

- признак зависит от конкретной реализации сервера;
- сам по себе редко достаточен без других сигналов.

## 6. Сопоставление алгоритмов с типами атак

| Тип атаки | Основные признаки | Наиболее релевантные алгоритмы |
|-----------|-------------------|--------------------------------|
| C2 over DNS | регулярные запросы, TXT polling | `C2_BEACON`, `C2_TXT_REQUEST` |
| Data exfiltration | entropy, encoded labels, много поддоменов | `HIGH_ENTROPY`, `HEX_SUBDOMAIN`, `BASE64_SUBDOMAIN`, `MANY_SUBDOMAINS` |
| IP-over-DNS | высокий rate, `NULL`, плотные ответы | `HIGH_RATE`, `NULL_RECORD`, `MANY_ANSWERS` |

Важно: детекторы работают не по имени инструмента и не по строке `attack.test`, а по наблюдаемым признакам трафика.

## 7. Глобальные ограничения текущей реализации

### 7.1 Ограничения захвата

- анализируется только `UDP/53`;
- BPF-логика использует IPv4-offset и отдельной ветки для IPv6 сейчас нет;
- DNS over TCP, DoH, DoT, DoQ не покрываются;
- при неполном payload событие превращается в `<unparseable>`.

### 7.2 Ограничения парсинга и агрегации

- `base_domain` считается как две последние метки, без Public Suffix List;
- `parse_dns_name()` пытается работать с compression pointers, но анализ ограничен копией payload в `128` байт;
- долгие и редкие кампании могут не накапливать достаточно сэмплов для C2-beacon;
- память детекторов ограничена LRU/FIFO, поэтому состояние старых ключей вытесняется.

### 7.3 Ограничения эксплуатационной готовности

- `pod_resolver` делает запрос к Kubernetes API с `limit=500` без пагинации;
- метрики `dns_events_by_process` и `dns_events_by_pod` потенциально создают высокую cardinality;
- whitelist TXT и cluster DNS влияет на FP/FN и требует сопровождения;
- система остаётся эвристической: она интерпретируема, но не гарантирует покрытие всех возможных реализаций DNS-туннелей.

---

## 8. Что важно написать в ВКР

Для диссертации корректно формулировать результат так:

- система детектирует DNS-туннелирование по поведенческим и статистическим признакам;
- алгоритмы не завязаны на конкретный домен атаки;
- экспериментально подтверждена эффективность подхода на ограниченном наборе инструментов и сценариев;
- полнота покрытия всех возможных DNS-туннелей не доказывается и должна быть обозначена как ограничение исследования.
