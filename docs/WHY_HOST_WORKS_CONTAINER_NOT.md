# Почему на обычном Linux работает, а в контейнере нет (unparseable domain)

## «eBPF же для того и нужен, чтобы читать любой процесс на ноде?»

Да — в том смысле, что eBPF **видит любой процесс на ноде**: kprobe на `udp_sendmsg` срабатывает для **любого** процесса (на хосте или в контейнере), который отправил UDP. В момент срабатывания мы в контексте **именно этого** процесса («current» = тот, кто вызвал syscall). То есть мы действительно «привязаны» к любому процессу на ноде.

Но eBPF даёт тебе в первую очередь **ядро**: системные вызовы, указатели, структуры ядра. А **user-память процесса** (буфер с DNS) — это не ядро, а память пользовательского пространства. Читать её можно только через `bpf_probe_read_user()`, и ядро **не всегда это разрешает**: для процессов в отдельном **user namespace** (типичный контейнер) ядро часто отказывает в чтении этой памяти — из соображений изоляции. То есть «видеть любой процесс» и «читать user-память любого процесса» — разные вещи: второе ядро ограничивает. Поэтому на голом хосте (один user namespace) читается, в контейнере — нет.

---

## Коротко

- **Передача eBPF → userspace тут ни при чём.** Perf buffer работает нормально, события доходят, в них есть и `data_len`, и `dns_data[256]`.
- **Проблема в том, откуда в ядре мы читаем данные.** Мы читаем память процесса (user-space буфер с DNS). На хосте эта память читается правильно, в контейнере — нет, и в буфер попадает мусор. Perf buffer честно тащит этот мусор в userspace — поэтому и получается unparseable.

---

## Где в цепочке проблема

```
[Процесс пишет DNS в свой буфер]  →  [Ядро: udp_sendmsg вызывается]
                                              ↓
[ eBPF: kprobe на udp_sendmsg ]
   - берём указатель на этот буфер из msg_iter
   - читаем 256 байт: bpf_probe_read_user() или bpf_probe_read_kernel()
   - кладём в event.dns_data и event.data_len
                                              ↓
[ eBPF: events.perf_submit(ctx, &event) ]  ←  сюда уже попадают ПРАВИЛЬНЫЕ или НЕПРАВИЛЬНЫЕ байты
                                              ↓
[ Perf buffer: копирует event в userspace ]
                                              ↓
[ Python: получает event, парсит event.dns_data ]
   - если в dns_data лежат настоящие DNS-байты → домен парсится
   - если лежит мусор (нули, чужие адреса) → <unparseable>
```

Сломано **до** perf buffer: мы в ядре читаем не ту память (или не можем прочитать нужную). Perf buffer просто доставляет то, что мы в него положили.

---

## Почему на обычном Linux работает

- Процесс (например `nslookup`, браузер, systemd-resolved) живёт в **том же** user namespace, что и ядро.
- Указатель из `iov_iter` указывает на **user-space** буфер этого процесса с DNS-запросом.
- **`bpf_probe_read_user()`** в этом контексте успешно читает эту user-память → в `event.dns_data` попадают настоящие байты DNS → в userspace парсер видит нормальный payload → домен извлекается.

То есть: источник данных (чтение user-буфера) на хосте корректен, perf buffer лишь передаёт уже правильные байты.

---

## Почему в контейнере не работает

- Контейнер обычно в **отдельном user namespace** (или с другими ограничениями).
- Указатель из `iov_iter` по-прежнему указывает на user VA процесса (где лежит DNS), но:
  - **`bpf_probe_read_user()`** в контексте eBPF в этом окружении **не может** прочитать эту user-память (права/контекст/namespace) → возвращает ошибку.
- Код делает fallback на **`bpf_probe_read_kernel()`** по тому же адресу (user VA).
  - Для **kernel** VA этот хелпер читает ядерную память.
  - Для **user** VA ядро не падает, но отдаёт не содержимое буфера процесса, а то, как этот адрес отображается в другом контексте (например нулевая страница, или другое отображение) → в `event.dns_data` попадает **мусор** (нули в byte[12], посторонние байты и т.д.).
- **Perf buffer по-прежнему работает:** он передаёт 256 байт из `event.dns_data` в userspace. Но там уже не DNS, а мусор → парсер выдаёт `<unparseable>`.

Итого: способ передачи (perf buffer) тот же, меняется только **качество данных**, которые мы в ядре записали в `event.dns_data` — в контейнере мы туда записываем неверные байты.

---

## Есть ли другие способы передать данные из eBPF в userspace?

Да. Основные варианты:

| Механизм | Назначение |
|----------|------------|
| **Perf buffer** | Поток событий: ядро пишет, userspace читает (poll). То, что мы используем. |
| **Ring buffer** (BPF_MAP_TYPE_RINGBUF) | То же по смыслу, но новее и эффективнее (ядерные 5.8+). |
| **Hash/Array map** | Ключ–значение. Удобно для счётчиков, состояний, небольших структур. Не поток событий. |
| **Perf events (perf_event_open)** | Низкоуровневый вариант для сэмплов/событий. BCC/perf buffer поверх этого строит. |

Если бы мы переключились на ring buffer или писали в map по ключу — **проблема не исчезла бы**: мы по-прежнему в ядре заполняем `dns_data` чтением из процесса. Плохие байты были бы в map или в ring buffer вместо perf buffer. Проблема не в выборе механизма передачи, а в том, **что мы читаем в ядре**.

---

## Для чего тогда perf buffer?

Perf buffer нужен именно для **передачи** событий из eBPF в userspace в реальном времени (без блокировки ядра, с минимальными задержками). Он для этого и используется: мы в ядре формируем `struct dns_event` (включая `dns_data`), делаем `perf_submit`, и Python получает этот event и парсит домен. Передача работает. Дело не в perf buffer, а в том, что в `dns_data` в контейнере мы изначально кладём неверные данные из-за неудачного чтения user-памяти.

---

## Итог

| Вопрос | Ответ |
|--------|--------|
| Почему на хосте ок, в контейнере нет? | На хосте `bpf_probe_read_user()` успешно читает буфер процесса → в event попадают настоящие DNS-байты. В контейнере user read не срабатывает, fallback `bpf_probe_read_kernel()` по user VA даёт мусор → в event попадает не DNS. |
| Виноват ли perf buffer? | Нет. Он только передаёт то, что мы положили в `event` в ядре. Данные портятся до передачи. |
| Есть ли другие способы передать данные eBPF → userspace? | Да (ring buffer, map и т.д.). Они не решат unparseable: проблема в источнике данных (чтение user-буфера в контейнере), а не в способе доставки. |
| Что по сути сломано? | Чтение **user-space** памяти процесса из eBPF в окружении контейнера (user namespace/контекст). Чтобы снова получать нормальный payload, нужно либо читать там, где данные уже в ядре (другой хук, например по skb после копирования в сетевой стек), либо не полагаться на чтение user-буфера в контейнере (например, CoreDNS как источник доменов). |
