# Анализ кода DNS Tunnel Monitor

Документ фиксирует результаты разбора кодовой базы: критические недостатки, улучшения детекторов, рефакторинг и идеи на будущее.

---

## 1. Критично: время не передаётся в детекторы (C2 и IP-over-DNS)

### Проблема

**C2-детектор** (`detectors/c2.py`) считает «бикон» (регулярность запросов по интервалам):
- использует `event.get('timestamp_ns', 0)` и строит интервалы между запросами;
- при `timestamp_ns == 0` интервалы не считаются, условие `len(timestamps) >= self.MIN_SAMPLES and timestamp` не выполняется;
- в результате **C2 beacon-детекция фактически не работает**.

**IP-over-DNS детектор** (`detectors/ip_over_dns.py`) считает rate в скользящем окне:
- использует `timestamp_ns` для окна и расчёта запросов в секунду;
- при отсутствии времени окно не обновляется, rate считается некорректно;
- в результате **логика HIGH_RATE и окна не работает как задумано**.

В **loader** при сборке `normalized` словаря **нет поля `timestamp_ns`**. В **event_handler** в `event_data` для `tunnel_detector.analyze()` тоже **нет `timestamp_ns`** (и `direction`). Детекторы получают события без времени.

### Рекомендация

1. **loader.py**: при создании события в `_perf_cb` добавить метку времени (достаточно userspace):
   ```python
   import time
   normalized = {
       ...
       "timestamp_ns": time.time_ns(),
   }
   ```
2. **event_handler.py**: в `event_data` для `tunnel_detector.analyze()` добавить `timestamp_ns` и при необходимости `direction`, чтобы C2 мог учитывать только query (beacon обычно по исходящим запросам).
3. Опционально: в BPF добавить `bpf_ktime_get_ns()` в структуру события и в `event_struct.py` — для более точного порядка событий; для детекции регулярности интервалов userspace `time.time_ns()` обычно достаточно.

## 2. Детекторы: улучшения и ограничения

### 2.1 C2

- **Регулярность (beacon)** — после добавления `timestamp_ns` начнёт работать; имеет смысл считать интервалы только по **query** (не по response), иначе ответы смешают картину.
- **C2_TXT_REQUEST** — срабатывает на любой TXT (type 16), кроме доменов, оканчивающихся на `.google.com`, `.microsoft.com`, `.cloudflare.com`. Много легитимного TXT (SPF, DKIM, DMARC, верификация и т.д.) даёт ложные срабатывания. Варианты: расширить whitelist, считать TXT подозрительным только в комбинации с другими признаками (например, высокой энтропией/длиной поддомена) или вынести в конфиг.
- **Пороги** — `MIN_SAMPLES=5`, `REGULARITY_THRESHOLD=0.15`, `avg_interval > 5` захардкожены; удобно вынести в конфиг/env.

### 2.2 Exfil

- **Память** — `subdomain_counts[base_domain]` и `query_history` в C2, `request_counts` в IP-over-DNS растут без ограничений. При долгой работе или большом числе доменов возможен рост потребления памяти. Имеет смысл ввести TTL или максимальный размер структур (например, вытеснение старых ключей или LRU).
- **Пороги** — энтропия, длина домена, число поддоменов захардкожены; вынести в конфиг для настройки под окружение.

### 2.3 IP-over-DNS

- **NULL_RECORD (type 10)** — одно срабатывание на тип 10 сразу даёт подозрение. Легитимное использование NULL редко, но возможно; можно требовать комбинацию с HIGH_RATE или MANY_ANSWERS.
- **Окно и rate** — после добавления `timestamp_ns` логика окна и HIGH_RATE заработает; при необходимости подправить `WINDOW_NS` и `RATE_THRESHOLD`.

### 2.4 Общее по детекторам

- Единый контракт: все детекторы принимают один и тот же `event` с полным набором полей (в т.ч. `timestamp_ns`, `direction`, `client_pod` при необходимости). Тогда не нужно вести отдельный «минимальный» `event_data` в event_handler.
- Конфигурируемые пороги (файл конфига или env) уменьшат необходимость менять код при тюнинге под разные сети.
- Юнит-тесты на детекторы (мок-события с разными domain/dns_type/timestamp_ns) помогут не ломать логику при рефакторинге.

## 3. Рефакторинг

### 3.1 Событие для детекторов

Сейчас в **event_handler** вручную собирается урезанный словарь:

```python
event_data = {
    "domain": domain,
    "dns_type": dns_type,
    "dns_answers": dns_answers,
    "cgroup_id": event.get("cgroup_id", 0),
}
```

Детекторам не передаются `timestamp_ns`, `direction`, `client_pod`. Варианты:

- Передавать в `tunnel_detector.analyze(event)` **полный** `event` (тот же, что приходит из loader с добавленным `timestamp_ns`). Детекторы сами берут нужные поля — проще расширять и не забывать новые поля.
- Либо завести один модуль/класс «схема события для детекторов» и собирать событие в одном месте (например, в loader или в event_handler), а детекторы получают только этот объект.

### 3.2 Конфиг

- **config.py** — сейчас только путь к BPF и env-имена. Имеет смысл добавить секцию порогов детекторов (или загрузку из YAML/env), чтобы не хардкодить в C2/Exfil/IP-over-DNS.
- Переменные вроде `REGULARITY_THRESHOLD`, `ENTROPY_THRESHOLD`, `RATE_THRESHOLD` и т.д. вынести в конфиг с разумными дефолтами.

### 3.3 Метрики и инициализация

- В **metrics.py** дублируется список метрик при `FLASK_AVAILABLE` и в ветке `else` (обнуление). Можно держать один список имён/объектов и в ветке без Flask подменять объекты на no-op или заглушки, чтобы не дублировать.
- `_init_metrics()` — часть метрик инициализируется с `inc(0)`/`set(0)` для явного появления в Prometheus; при добавлении новых метрик нужно не забыть добавить их и сюда.

### 3.4 Именование и структура

- **C2** в сообщении пользователя («c3 requires time») — по смыслу это C2 (Command & Control); в коде и доке везде C2, ок.
- **detectors/tunnel.py** — один класс-агрегатор, вызывает C2/Exfil/IP-over-DNS. Структура понятная; при росте числа детекторов можно завести регистрацию детекторов (список/плагины) и единый цикл `for d in detectors: ...`.

## 4. Прочее

### 4.1 BPF

- В событие из ядра передаётся только direction, cgroup_id, payload. Для точного порядка событий можно добавить в структуру события в C и в Python поле `timestamp_ns` и заполнять его через `bpf_ktime_get_ns()` в BPF. Требует изменения структуры и синхронизации C/Python.
- Сейчас для детекции «регулярности» и «rate» достаточно времени в userspace при приходе события.

### 4.2 Тесты

- Нет автоматических тестов в репозитории. Полезно добавить:
  - тесты парсинга DNS (`dns_parsing`: domain, type, entropy);
  - тесты детекторов на наборах мок-событий (с и без `timestamp_ns`, разные домены, типы, интервалы);
  - тесты PodResolver (например, извлечение UID из пути cgroup) — при возможности без реального ядра/файловой системы (моки).

### 4.3 Документация

- Ограничения (process best-effort, только UDP, детекторы — эвристики) уже отражены в README.
- В README или отдельном файле можно кратко описать логику каждого детектора (что считает C2/Exfil/IP-over-DNS и по каким полям), чтобы проще настраивать пороги и понимать алерты.

## 5. Приоритеты

| Приоритет | Задача | Эффект |
|-----------|--------|--------|
| Высокий | Добавить `timestamp_ns` в событие (loader) и в `event_data` (event_handler) | Включит C2 beacon и IP-over-DNS rate/окно |
| Высокий | Передавать в детекторы полное событие (или как минимум timestamp_ns + direction) | Единый контракт, меньше ошибок при расширении |
| Средний | Конфигурируемые пороги детекторов (config/env) | Тюнинг без правок кода |
| Средний | Ограничение роста памяти в детекторах (TTL/LRU для history/counts) | Стабильная работа при долгом uptime |
| Средний | Смягчить C2_TXT (whitelist/комбинация с другими признаками) | Меньше ложных срабатываний по TXT |
| Низкий | Юнит-тесты для парсинга и детекторов | Уверенность при изменениях |
| Низкий | Опционально: timestamp в BPF (bpf_ktime_get_ns) | Более точный порядок событий |

## 6. Краткое резюме

- **Главная проблема**: детекторы C2 (beacon) и IP-over-DNS (rate/окно) завязаны на `timestamp_ns`, но это поле ни в событии из loader, ни в `event_data` для analyze не передаётся, поэтому соответствующая логика не работает.
- **Минимальный фикс**: добавить `timestamp_ns = time.time_ns()` в loader при формировании события и передать `timestamp_ns` (и при необходимости `direction`) в `event_data` в event_handler.
- Дальше имеет смысл: единый контракт события для детекторов, вынос порогов в конфиг, ограничение памяти в детекторах и тесты.
