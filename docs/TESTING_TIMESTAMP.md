# Проверка работы timestamp (C2 beacon и IP-over-DNS rate)

Проверять лучше **сначала локально на Linux VM**: трафик предсказуемый, легко воспроизвести регулярные запросы и всплеск частоты. В кластере — для проверки на реальном трафике после успешной локальной проверки.

---

## 1. Локально на Linux VM (рекомендуется)

### Требования

- Linux, cgroup v2, BCC, root или CAP_BPF/CAP_NET_ADMIN.
- Пакеты уходят через тот же cgroup, к которому привязан монитор (обычно корневой cgroup хоста).

### 1.1 Запуск монитора

```bash
cd /path/to/repo
sudo CGROUP_PATH=/sys/fs/cgroup python3 -m dns_tunnel_monitor
```

Оставьте терминал с выводом открытым. В логах должны появляться строки вида `UDP QUERY` / `UDP RESPONSE` при любом DNS-трафике.

### 1.2 Проверка C2 beacon (регулярность интервалов)

Нужно сгенерировать **не менее 5 запросов** к **одному и тому же домену** с **стабильным интервалом > 5 секунд** (например, каждые 10 с).

В **втором терминале** на той же машине:

```bash
# Интервал 10 с, минимум 6 запросов (чтобы было 5+ интервалов для расчёта)
for i in 1 2 3 4 5 6 7; do
  nslookup test-beacon-check.example.com
  sleep 10
done
```

**Что смотреть в логе монитора:** после 5–6 запросов к `test-beacon-check.example.com` должна появиться строка с подозрением, например:

```text
SUSPICIOUS [C2]: C2_BEACON(interval=10.0s, regularity=...)
```

Если такой строки нет — проверьте, что в первом терминале в событиях есть `timestamp_ns` (можно временно добавить `print(event.get('timestamp_ns'))` в event_handler или убедиться, что версия кода с `timestamp_ns` в loader развёрнута).

### 1.3 Проверка IP-over-DNS (высокий rate)

Нужно сгенерировать **больше 50 запросов в секунду** к одному домену (в пределах одного 10‑секундного окна).

Во втором терминале:

```bash
# ~100 запросов подряд к одному домену (зависит от скорости, должно быть > 50/с)
for i in $(seq 1 100); do nslookup test-rate-check.example.com & done
wait
```

**Что смотреть в логе монитора:** причина вида `HIGH_RATE(.../sec)` и тип угрозы `TUNNEL`. Если нагрузка не дотянула до 50/с, увеличьте число итераций или уменьшите паузы.

### 1.4 Одной командой (beacon + rate)

```bash
# Сначала beacon (регулярные запросы)
for i in 1 2 3 4 5 6 7; do nslookup beacon.example.com; sleep 10; done

# Потом burst для rate
for i in $(seq 1 80); do nslookup rate.example.com & done; wait
```

В логах монитора должны появиться оба типа срабатываний (C2_BEACON и HIGH_RATE).

## 2. В кластере

После того как локально убедились, что C2 и rate срабатывают:

1. Разверните актуальный образ с `timestamp_ns` в событии и перезапустите поды.
2. **Beacon:** воспроизвести регулярные запросы из пода (cron job или цикл с `sleep` и `nslookup`/`dig` к одному домену, интервал 6–10 с, не менее 5 запросов).
3. **Rate:** из пода выполнить серию быстрых запросов к одному домену (скрипт с циклом без пауз или с очень короткой паузой).
4. Смотреть логи пода монитора: `kubectl logs -n default -l app.kubernetes.io/name=dns-tunnel-monitor -f` — искать `SUSPICIOUS [C2]` и `SUSPICIOUS [TUNNEL]` с нужными причинами.
5. В Grafana/Prometheus можно смотреть `dns_suspicious_total{threat_type=~"C2|TUNNEL"}` после теста.

В кластере сложнее отсечь чужой трафик и точно знать момент срабатывания, поэтому локальная проверка предпочтительна для валидации логики.

## 3. Юнит-тесты (без BPF, только детекторы)

В репозитории есть тесты в `tests/test_timestamp_detection.py`: моки событий с `timestamp_ns`, проверка C2 beacon и IP-over-DNS rate. Запуск **без ядра/BCC**, только логика детекторов.

```bash
cd /path/to/dns_tunnel_monitor
pip install pytest   # если ещё не установлен
pytest tests/ -v
```

Тесты проверяют:
- регулярные запросы (каждые 10 с) → срабатывает `C2_BEACON`;
- только query участвуют в beacon (response не добавляются в историю);
- много запросов за короткое время → срабатывает `HIGH_RATE`;
- тип NULL (10) → причина `NULL_RECORD`;
- при `timestamp_ns=0` beacon не срабатывает.

Успешный прогон pytest подтверждает, что алгоритмы с timestamp работают; для полной проверки с реальным трафиком используйте шаги из раздела 1 (локально на VM).

## 4. Кратко

| Что проверить | Где лучше | Как |
|---------------|-----------|-----|
| C2 beacon     | Локально  | Цикл: `nslookup <домен>; sleep 10` не менее 6 раз, смотреть лог на `C2_BEACON` |
| IP-over-DNS rate | Локально | Много быстрых `nslookup <домен>` подряд, смотреть лог на `HIGH_RATE` |
| Реальный трафик | Кластер | После успешной локальной проверки — те же сценарии из пода и логи/Grafana |

Сначала проверьте на Linux VM с описанными командами; после этого при необходимости повторите сценарии в кластере.
