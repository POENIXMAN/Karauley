# Что попробовать, чтобы user read работал в контейнере (kprobe, unparseable)

Цель: сделать так, чтобы `bpf_probe_read_user()` в kprobe успешно читал буфер процесса и в `dns_data` попадали настоящие DNS-байты. Ниже — что проверить и в каком порядке.

---

## 1. Что уже есть у тебя

В Helm уже включено:
- `privileged: true` — под имеет все capabilities, включая CAP_SYS_ADMIN, CAP_BPF, CAP_PERFMON и т.д.
- `hostNetwork: true`, `hostPID: true` — под видит сеть и процессы хоста.

Этого достаточно для **загрузки** eBPF и работы kprobe. Проблема не в правах **нашего** пода на загрузку, а в том, что в момент чтения ядро не даёт прочитать **user-память другого процесса** (того, кто вызвал `udp_sendmsg`), если тот процесс в отдельном user namespace.

---

## 2. Что проверить и попробовать

### 2.1. Явно задать runAsUser / runAsGroup (наш под)

Иногда при `privileged: true` образ всё равно запускает процесс не от root. Задать явно:

```yaml
# helm/values.yaml → daemonset
securityContext:
  privileged: true
  runAsUser: 0
  runAsGroup: 0
```

В шаблоне DaemonSet это должно попасть в `spec.template.spec.securityContext` (на уровень пода) или в `containers[].securityContext`. Перезапусти под и проверь логи (user_ok в eBPF debug).

---

### 2.2. hostUsers (Kubernetes 1.25+)

Если в кластере включены user namespaces для подов, наш мониторинг-под может быть в отдельном user namespace. Попробуй явно заставить его использовать user namespace хоста:

```yaml
# spec.template.spec
hostUsers: true
```

(В части версий K8s поле может называться иначе или требовать feature gate.) Идея: наш под тогда в том же user namespace, что и хост; это не гарантирует, что **целевой** процесс (отправляющий DNS) в том же NS, но исключает проблему «наш под в своём userns».

---

### 2.3. Диагностика: тестовый под без user namespace

Проверь гипотезу «мешает user namespace **отправителя**»:

1. Создай под, который точно **не** в user namespace и шлёт DNS:
   - `runAsUser: 0`
   - без `hostUsers: false` (т.е. обычный под без userns).
2. В этом поде выполни: `nslookup google.com` (или любой запрос на порт 53).
3. Посмотри логи dns-monitor: для этого запроса домен должен появиться нормально или с `user_ok > 0` в eBPF debug.

Если для этого пода домены парсятся, а для остальных (CoreDNS, другие приложения) — нет, значит проблема в user namespace (или контексте) **процессов, которые шлют DNS**, а не в правах нашего пода.

---

### 2.4. Маленькое чтение в eBPF (12 байт)

Чтобы понять «нет прав» vs «не тот размер», добавь в eBPF пробу только на 12 байт (DNS header):

- Сначала вызвать `bpf_probe_read_user(dst, 12, src)`.
- По результату: успех → значит user read в принципе возможен (тогда можно смотреть на 256 байт, границы страниц и т.д.); ошибка → значит в этом окружении user-память целевого процесса читать нельзя (namespace/права).

Это не «фикс прав», а диагностика: после неё будет ясно, есть ли смысл ковырять capabilities дальше или дело в namespace отправителя.

---

### 2.5. Capabilities, если откажешься от privileged

Если захочешь убрать `privileged: true` и дать только нужные права, обычно нужны как минимум:

- `CAP_BPF` — загрузка BPF-программ
- `CAP_PERFMON` — perf buffer / perf events
- `CAP_SYS_ADMIN` — часть операций с eBPF/maps
- `CAP_SYS_PTRACE` — иногда связывают с доступом к памяти других процессов (ptrace); для eBPF чтения user-памяти явно в документации не всегда описано, но попробовать стоит.

Пример в values:

```yaml
securityContext:
  capabilities:
    add:
      - SYS_ADMIN
      - SYS_PTRACE
      - NET_ADMIN
      - BPF
      - PERFMON
  runAsUser: 0
  runAsGroup: 0
```

Сейчас у тебя и так всё это даёт `privileged`, так что для «нормально читала» важнее п. 2.1–2.4.

---

### 2.6. Рантайм на ноде (user namespace для контейнеров)

Если на ноде включён user namespace для контейнеров (например, в containerd/cri-o включён userns-remap или аналог), то процессы в подах живут в отдельном user namespace. В таком случае `bpf_probe_read_user()` по их user VA может не срабатывать из-за политики ядра, и «права» нашего пода это не исправят.

Что сделать:
- Проверить конфиг containerd/cri-o на ноде: не включён ли user namespace remapping для подов.
- Если включён и его нельзя отключить — тогда «нормально читать» user-буфер в kprobe в контейнерах может быть недоступно, и разумный обход — брать домены из CoreDNS (см. COREDNS_AS_DNS_SOURCE.md).

---

## 3. Краткий порядок действий

1. В Helm выставить **runAsUser: 0**, **runAsGroup: 0** для пода dns-monitor, перезапустить, посмотреть eBPF debug (user_ok).
2. Запустить **тестовый под с runAsUser: 0**, сделать из него DNS-запрос, проверить, парсится ли домен и растёт ли user_ok.
3. В eBPF добавить **пробу чтения 12 байт** через `bpf_probe_read_user` и по логам понять: user read вообще возможен или нет.
4. Если кластер 1.25+ и есть user namespaces — попробовать **hostUsers: true** для нашего пода.
5. При необходимости проверить **рантайм на ноде** (user namespace для контейнеров) и иметь в виду fallback на CoreDNS, если user read в таких контейнерах ядро не разрешает.

Итог: «нормально читала» упирается не в perf buffer и не только в права пода монитора, а в то, разрешает ли ядро читать user-память **процесса, который вызвал udp_sendmsg**. Права и runAsUser проверяем в первую очередь; если не помогло — смотрим user namespace отправителя и рантайм ноды.
