# Дальнейший план работ

Документ фиксирует, что уже есть в проекте, какие задачи критичны для сильной версии ВКР, какие технические улучшения разумны, а какие лучше считать опциональными.

---

## 1. Что уже есть

На текущий момент у проекта уже есть хороший базис:

- Kubernetes-кластер с рабочим `dns-tunnel-monitor` в формате `DaemonSet`;
- eBPF-захват DNS на уровне `cgroup_skb`;
- атрибуция `cgroup_id -> pod/process`;
- эвристические детекторы для `C2`, `EXFIL`, `IP-over-DNS`;
- structured JSON logging для событий;
- `analyze.py` для расчёта confusion matrix и метрик;
- Grafana/Prometheus с базовыми метриками;
- baseline- и attack-манифесты для воспроизводимого тестирования;
- сильный результат `Phase C` при `GT by domain` и `threshold=3`.

Это уже достаточно, чтобы защищать идею как работающий исследовательский прототип.

---

## 2. Что критично доделать именно для ВКР

### 2.1 Доделать экспериментальную часть

Это самый ценный следующий шаг.

Нужно:

1. повторить `Phase C` минимум `2-3` раза;
2. повторить `Phase B` на текущем коде;
3. построить итоговую таблицу по всем фазам в одной версии методологии;
4. построить график зависимости метрик от `threshold`;
5. зафиксировать detection latency по каждому инструменту.

Почему это важно:

- это укрепляет доказательность;
- показывает воспроизводимость;
- превращает результаты из “одного удачного прогона” в нормальную экспериментальную базу.

### 2.2 Подготовить визуализации для текста ВКР

Минимальный набор:

- архитектурная схема потока `pod -> eBPF -> userspace -> detector -> metrics`;
- схема ground truth и фаз `A/B/C`;
- столбчатые графики `Precision / Recall / F1 / FPR`;
- график `threshold -> metrics`;
- таблица и график “до/после исправлений”.

### 2.3 Аккуратно оформить ограничения

Это тоже обязательно:

- только `UDP/53`;
- без IPv6-ветки;
- без `DoH/DoT/DoQ`;
- ограниченная обобщаемость;
- `<unparseable>` как источник потерь;
- эвристический характер системы.

Хорошо описанные ограничения не ослабляют ВКР, а наоборот делают её честной и зрелой.

## 3. Сравнение с другими подходами

Да, сравнивать с альтернативами стоит. Но лучше сравнивать не “один-в-один продукт против продукта”, а **классы подходов**.

### 3.1 Реалистичные точки сравнения

#### Suricata

Что это:

- сетевой IDS/IPS;
- умеет анализировать DNS и применять сигнатуры/правила.

Почему интересно:

- это понятный baseline для сигнатурного/сетевого подхода;
- можно показать, что твой модуль работает внутри кластера и даёт pod attribution без внешнего tap/span.

Ограничение сравнения:

- Suricata и твой модуль находятся в разной архитектурной точке;
- потребуется отдельная интеграция и сбор DNS-трафика.

#### Zeek

Что это:

- мощная система сетевой телеметрии и scripting для DNS/HTTP/TLS.

Почему интересно:

- хороший эталон для rich network visibility;
- можно сравнить выразительность DNS-логов и сложность эксплуатации.

Ограничение:

- тяжелее по эксплуатации;
- не является Kubernetes-native решением сам по себе.

#### CoreDNS logs + SIEM/Sigma/Loki

Что это:

- подход “логировать DNS на резолвере и искать аномалии в логах”.

Почему интересно:

- очень практичный baseline;
- легко объяснить, что твой модуль работает раньше по пути и имеет другой уровень контекста.

Ограничение:

- такие логи не всегда удобно связывать с исходным подом;
- видимость ограничена тем, что реально прошло через резолвер.

#### Falco / Tetragon / Cilium Hubble

Что это:

- смежные инструменты облачной безопасности и observability.

Почему интересно:

- их полезно упомянуть в related work для Kubernetes security.

Но:

- они не являются прямыми аналогами DNS tunnel detector по payload-level логике;
- это скорее соседние, а не конкурентные решения.

### 3.2 Что стоит написать в ВКР

Корректная позиция:

> Существуют сетевые и runtime-ориентированные средства мониторинга, которые могут косвенно выявлять подозрительный DNS-трафик, однако они либо не ориентированы специально на DNS-туннели в Kubernetes, либо требуют отдельной инфраструктуры захвата, либо не дают нативной pod-level атрибуции в той форме, в которой это реализовано в предлагаемом модуле.

### 3.3 Практический план сравнения

Если времени мало, лучший вариант:

1. сравнить архитектурно и качественно с `Suricata`, `Zeek`, `CoreDNS logs`;
2. не обещать полный экспериментальный benchmark против всех;
3. если хватит времени, сделать хотя бы один демонстрационный сценарий с `Suricata` или с `CoreDNS + rules`.

## 4. Технические улучшения кода

### 4.1 Критичные улучшения

#### Поддержка IPv6

Почему важно:

- часть `<unparseable>` очень вероятно связана именно с IPv6;
- это прямо влияет на recall.

Что сделать:

- в BPF добавить разбор версии IP;
- использовать разные offsets для IPv4 и IPv6;
- повторить тесты после правки.

#### Проверить и укрепить `pod_resolver`

Что проверить:

- лимит `pods?limit=500` без пагинации;
- поведение на больших кластерах;
- поведение при RBAC-ошибках;
- устойчивость к ситуациям, где `cgroup_id` не разрешается.

Что можно улучшить:

- пагинация по API;
- более явные fallback-метрики;
- отдельные счётчики ошибок резолвера.

#### Проверить metric cardinality

Почему важно:

- метрики по `process` и `client_pod` могут взрываться по cardinality;
- это проблема уже не детекции, а эксплуатации и Prometheus.

Что можно сделать:

- ограничить/агрегировать labels;
- вынести подробную статистику в логи, а не в time series.

### 4.2 Средний приоритет

#### Рефакторинг структуры кода

Имеет смысл пройтись по:

- разделению parsing / attribution / detection / reporting;
- тестам для каждого detector отдельно;
- явным dataclass/pydantic-структурам события вместо “словарь везде”.

#### Безопасность и эксплуатация

Проверить:

- действительно ли все зависимости нужны;
- минимальны ли container privileges;
- можно ли сократить surface area контейнера;
- нет ли избыточных capabilities и лишних пакетов в образе;
- как ведёт себя приложение при ошибках BPF, K8s API и metrics server.

#### Нагрузочные и долгие тесты

Полезно проверить:

- память детекторов на длинных окнах;
- рост LRU-структур;
- нагрузку на CPU при высоком DNS rate;
- стабильность DaemonSet при длительной работе.

## 5. Алерты и operational readiness

Это очень разумное следующее направление.

Что есть сейчас:

- Prometheus-метрики;
- Grafana-dashboard.

Чего не хватает:

- правил алертинга;
- понятных порогов;
- runbook “что делать при алерте”.

Минимальный практический набор алертов:

1. рост `dns_suspicious_total` по `threat_type`;
2. всплеск `dns_events_by_pod` для одного пода;
3. всплеск `NULL_RECORD`/`HIGH_RATE`/`MANY_SUBDOMAINS` в логах;
4. деградация самого мониторинга: нет метрик, нет readiness, ошибки резолвера.

Для ВКР достаточно описать проект алертинга и показать 1-2 демонстрационных правила.

## 6. ML: стоит ли добавлять

Короткий ответ: можно, но не как ближайший шаг.

### 6.1 Почему ML может быть полезен

- может помочь ловить более сложные комбинации признаков;
- может снизить зависимость от ручных порогов;
- может помочь на “пограничных” случаях.

### 6.2 Почему это не быстрый апгрейд

Для ML потребуется:

- датасет;
- стабильная разметка;
- разделение train / validation / test;
- сравнение с эвристическим baseline;
- борьба с drift;
- интерпретация результатов;
- интеграция inference в runtime.

То есть это уже отдельный исследовательский трек, а не небольшая доработка.

### 6.3 Если всё же идти в ML

Практичный путь:

1. сначала собрать хороший датасет из текущих JSONL;
2. построить offline-признаки:
   - entropy;
   - длина;
   - digit ratio;
   - qtype;
   - answers count;
   - rate;
   - число уникальных subdomains;
   - регулярность;
   - длина labels;
   - доля encoded labels;
3. обучить простой интерпретируемый baseline:
   - Logistic Regression;
   - Random Forest / XGBoost;
4. сравнить его не “в вакууме”, а против текущей эвристики.

Если ML не превосходит текущие правила заметно, его лучше оставить как future work.

---

## 7. Рекомендуемый порядок действий

Если идти по приоритету и пользе для ВКР, я бы рекомендовал такой порядок:

1. Повторить `Phase B` и `Phase C` на текущем коде.
2. Построить итоговые графики и таблицы для ВКР.
3. Добавить поддержку IPv6 или хотя бы точно подтвердить вклад IPv6 в `<unparseable>`.
4. Настроить 1-2 рабочих алерта в Prometheus/Grafana.
5. Сделать короткий related work / comparison с `Suricata`, `Zeek`, `CoreDNS logs`.
6. Проверить codebase на эксплуатационные риски: privileges, dependencies, cardinality, pod resolver.
7. Только потом решать, нужен ли ML как отдельное направление.

---

## 8. Итог

У проекта уже есть сильная исследовательская основа. Сейчас наибольшую отдачу дадут не новые эвристики, а:

- добор доказательной экспериментальной базы;
- аккуратное оформление графиков и ограничений;
- несколько точечных инженерных улучшений;
- лёгкое усиление эксплуатационной части через алерты и code review по рискам.

Именно это сильнее всего повысит качество ВКР и убедительность результата.
