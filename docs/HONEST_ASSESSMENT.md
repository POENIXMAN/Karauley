# Честная оценка проекта DNS Tunnel Monitor

Дата: 2026-03-01  
Версия: 2 (с учётом результатов валидации из VALIDATION_FINDINGS.md)

---

## 1. Как я понимаю ситуацию

### Что есть

Прототип модуля детекции DNS-туннелей для Kubernetes. Архитектура:

```
eBPF (cgroup_skb, 43 строки C)
    → perf_buffer
        → Python userspace (loader → parser → event_handler → detectors)
            → stdout (цветной лог) + stderr (JSON) + Prometheus metrics (/metrics)
```

Компоненты:
- **BPF-программа** — перехватывает UDP пакеты на порт 53, захватывает первые 64 байта DNS payload + cgroup_id. Привязывается к cgroup_skb (egress + ingress).
- **3 детектора** — C2 beacon (регулярность запросов), Exfiltration (энтропия, кодированные поддомены, количество уникальных поддоменов), IP-over-DNS (rate, NULL record, MANY_ANSWERS).
- **Scoring** — взвешенная сумма причин, порог = 2.
- **Pod resolver** — cgroup_id → namespace/podname через BPF syscall / cgroup fs walk / K8s API.
- **Helm chart** — DaemonSet, privileged, hostNetwork, hostPID, ServiceAccount + RBAC, ServiceMonitor.
- **Тестовая инфраструктура** — K8s манифесты для baseline-трафика и атак, collect.sh, analyze.py.
- **Unit-тесты** — 1 файл, 5 тестов.

### Что проделано

- Исправлено 11 критических багов (утечки памяти, мёртвый код, некорректное определение query/response, unbounded структуры данных).
- Добавлена scoring-система, whitelist кластерного DNS и TXT-записей, structured JSON logging.
- **Проведена полная валидация:** Phase A (baseline, 522K событий), Phase B (iodine, dnscat2, DNSExfiltrator по отдельности), Phase C (смешанный трафик, 457K событий).

### Что показала валидация

| Факт | Результат |
|------|-----------|
| Модуль деплоится и работает на кластере | Да |
| Pod resolver резолвит cgroup_id → pod | Да |
| iodine ловится | Да (NULL_RECORD + MANY_SUBDOMAINS). По распарсенным событиям Precision=1, Recall=1 |
| dnscat2 ловится | Да, идеально. 2340/2340 TP, Precision=1, Recall=1 |
| DNSExfiltrator ловится | Частично. Precision=1, но Recall=0.40 из-за обрезки payload |
| Baseline FP | 0 при threshold=3, ~23 при threshold=2 из 450K+ clean событий |
| Detection latency | ~0.01 с |

## 2. Что действительно работает хорошо

### 2.1 Детекция по response-пакетам — сильная сторона

DNS-ответы парсятся стабильно. Все три tunnel tools обнаруживаются по ответам. Это подтверждено экспериментально:
- **dnscat2** — 100% detection rate, HEX_SUBDOMAIN + MANY_SUBDOMAINS
- **iodine** — 100% по распарсенным ответам, NULL_RECORD + MANY_SUBDOMAINS
- **DNSExfiltrator** — 100% precision по распарсенным событиям, HIGH_ENTROPY + MANY_SUBDOMAINS

### 2.2 Baseline чистый

Phase A: 522K событий, **0 FP** при threshold=3. Это отличный результат — детектор не кричит «волк» на пустом месте.

### 2.3 Scoring-система работает

Взвешенная комбинация сигналов (threshold=2 или 3) разделяет attack/legit. Это подтверждено Phase C: реальных FP на baseline-трафике ~23 из ~450K = 0.005%.

## 3. Проблемы, выявленные валидацией

### 3.1 IPv6 — главный источник `<unparseable>`

**Факт:** BPF читает payload с фиксированного offset 28 (IPv4: 20 IP + 8 UDP). Для IPv6 заголовок 40 байт → offset 48. При IPv6-трафике чтение с offset 28 даёт мусор → `<unparseable>`.

**Масштаб:** FN=2174 из 5996 событий iodine (36%) — все `<unparseable>`. Это query-пакеты, часто по IPv6.

**Влияние на ВКР:** Это основная причина низкого сырого Recall. Но это ограничение eBPF-захвата, не детектора. Для ВКР достаточно описать как «ограничение текущей реализации» и показать, что по распарсенным событиям детекция работает.

**Можно исправить?** Да. В BPF: прочитать первый байт, взять верхние 4 бита (IP version), выбрать offset. Оценка: 4-8 часов. Это **существенно** улучшит сырые метрики.

### 3.2 64 байта payload — подтверждённая проблема для exfil

**Факт:** DNSExfiltrator с 55-символьными чанками. Из 736 событий — 330 с `domain="0"` (только первый label, остальное обрезано).

**Влияние:** Recall DNSExfiltrator = 0.40 (сырой). По распарсенным событиям (294) Precision=1, но 330 событий потеряны.

**Парадокс:** dnscat2 с hex-поддоменами (~32 символа) умещается в 64 байта без проблем. iodine тоже. Проблема специфична для exfil с длинными чанками.

**Можно исправить?** Сложнее. Увеличение PAYLOAD_SAMPLE ранее ломало парсинг. Стоит **повторно исследовать** причину — возможно, проблема была в BPF verifier или в размере perf_buffer, а не в парсинге.

### 3.3 CoreDNS transit — артефакт методологии ground truth

**Факт:** DNS-запросы подов проходят через CoreDNS. Монитор видит тот же туннельный трафик дважды: от attack-пода и от CoreDNS. Ground truth по namespace считает CoreDNS-события как «legit» → они попадают в FP.

**Масштаб:** 3409 «FP» в Phase C, из которых ~3386 — это корректно обнаруженный атакующий трафик, транслируемый CoreDNS. Реальных FP только ~23.

**Влияние на ВКР:** Сырые метрики выглядят плохо (Precision=0.44). Но с пояснением — это сильная история: «детектор ловит туннель даже когда он проходит через CoreDNS, что подтверждает работоспособность на всех уровнях стека DNS».

**Решение:** Уже понятно — нужна разметка по домену (`*.attack.test` → attack) или исключение CoreDNS из подсчёта. Оба варианта реализуемы в analyze.py за 2-3 часа.

### 3.4 Пороги — подобраны, но не оптимизированы

| Порог | Значение | Статус после валидации |
|-------|----------|----------------------|
| `ENTROPY_THRESHOLD` | 4.1 | Работает: DNSExfiltrator детектируется с entropy 4.28–4.37 |
| `SCORE_THRESHOLD` | 2 | Работает, но threshold=3 даёт 0 FP на baseline (vs ~23 при 2) |
| `SUBDOMAIN_COUNT_THRESHOLD` | 40 | Работает: MANY_SUBDOMAINS(50) срабатывает на всех tools |
| `LENGTH_THRESHOLD` | 60 | **Мёртвый код.** При 64 байтах payload максимум ~45 символов |
| `REGULARITY_THRESHOLD` | 0.15 | Не проверен: C2_BEACON не сработал в тестах (dnscat2 ловился по HEX, не по beacon) |
| `RATE_THRESHOLD` | 150 | Не проверен: HIGH_RATE не сработал в тестах iodine |

**Важно:** C2_BEACON и HIGH_RATE — два из трёх «сильных» сигналов (вес 3) — **не сработали ни разу** в экспериментах. Детекция работала через MANY_SUBDOMAINS, NULL_RECORD, HEX_SUBDOMAIN, HIGH_ENTROPY. Это не значит, что beacon/rate бесполезны — dnscat2 мог не показать регулярный интервал, а iodine мог не превысить 150 req/s. Но это значит, что **эти два детектора не валидированы экспериментально**.

## 4. Вопросы, на которые ещё надо ответить

### Блок A: Углубление валидации

**A1.** C2_BEACON ни разу не сработал. Почему? Варианты:
- dnscat2 не показывает регулярные интервалы (CV > 0.15)
- Недостаточно событий за тестовый период
- `avg_interval > 5` слишком высокий порог
- **Действие:** Посмотреть распределение интервалов dnscat2 в логах. Если они нерегулярные — beacon-детекция не работает на этом инструменте. Попробовать Sliver/Cobalt Strike C2 с настраиваемым jitter.

**A2.** HIGH_RATE не сработал на iodine. Почему?
- RATE_THRESHOLD = 150 req/s — может быть слишком высоко для iodine в тестовом режиме
- Window 10 секунд — может быть слишком короткое или слишком длинное
- **Действие:** Посмотреть фактический rate iodine в логах. Если 50-100 req/s — снизить порог.

**A3.** DNSExfiltrator Recall=0.40. Можно ли улучшить без изменения BPF?
- Может ли парсер извлечь хоть что-то из обрезанного домена?
- Может ли детектор работать с частичным доменом (первый label)?
- **Действие:** Проанализировать 330 событий с `domain="0"` — что вообще парсится.

**A4.** Baseline при threshold=2 даёт 23 FP. Что это за домены?
- `www.googleapis.com` — зафиксировано. Почему? Какой reason?
- Это HIGH_ENTROPY? TXT? Можно ли добавить в whitelist?
- **Действие:** Выгрузить FP-домены baseline, проанализировать причины.

### Блок B: Методология

- Если один прогон — честно написать «результаты единичного эксперимента».

**B2.** Разметка по домену (вместо по поду) — когда реализуем?
- Это убирает артефакт CoreDNS и даёт честные метрики.

**B3.** ROC-кривая: как F1 зависит от score_threshold?

**D2.** Если нет времени на количественное сравнение — хотя бы «обзор существующих решений» с таблицей: Suricata (signature-based, не cgroup), Cilium Hubble (L7 visibility, CNI-specific), Falco (system calls, не DNS payload), наш модуль (cgroup_skb, DNS payload, CNI-agnostic).

### Блок E: Технические улучшения

**E1.** ~~Проверка возврата `bpf_skb_load_bytes`~~ — **не актуально:** в BPF используется **прямой доступ** (ctx->data / data_end), одна проверка границ `data + MIN_PKT_LEN > data_end` → при коротком пакете событие не шлётся. Ошибка «чтение за границей» невозможна — верификатор это гарантирует.

**E2.** IPv6 support в BPF — 4-8 часов, существенно улучшает сырой Recall (убирает 36% FN у iodine). С прямым доступом: прочитать байт 0 (version), ветка offset 28 vs 48, отдельная проверка длины под каждую ветку.

**E3.** `lost_cb` для perf_buffer — 30 минут, даёт метрику потерянных событий.

**E4.** Ограничение `stats["domains"]` (set → LRU) — 30 минут, убирает последнюю утечку памяти.

## 5. Оставшиеся технические проблемы (не опровергнутые валидацией)

### 5.1 Блокирующие вызовы в callback perf_buffer

`_perf_cb` вызывается для каждого DNS-пакета. `PodResolver` может делать:
- Обход до 50K директорий файловой системы
- HTTP-запрос к K8s API (list 500 pods, timeout 5s)

Кэш с TTL помогает после прогрева. Но при высокой нагрузке на холодный кэш — риск переполнения perf_buffer. **Валидация не показала проблем** (вероятно, нагрузка была умеренной и кэш прогревался быстро), но при 10K req/s на ноде может проявиться.

### 5.2 Оставшиеся утечки памяти

- `stats["domains"]` — `set()`, растёт бесконечно
- `ExfiltrationDetector.subdomain_counts` — число ключей (base_domain) не ограничено
- Prometheus metrics с label `client_pod` — cardinality при ротации подов

Для 10-минутного теста не проявятся. Для длительной работы (дни, недели) — проблема.

### 5.3 Flask dev server

Werkzeug dev server в production. Для PoC/ВКР — допустимо, но стоит упомянуть в ограничениях.

### 5.4 BPF: прямой доступ (direct access) вместо bpf_skb_load_bytes

В коде используется **прямой доступ** к пакету: `ctx->data`, `ctx->data_end`, одна проверка `data + MIN_PKT_LEN > data_end`, затем чтения вида `*(uint8_t *)(data + offset)` и цикл копирования payload.

**Плюсы для нашего кейса:**
- **Верификатор:** одна явная проверка границ — все последующие обращения в пределах `[data, data_end)` доказуемо безопасны. Нет зависимости от возврата helper’а.
- **Производительность:** нет вызовов `bpf_skb_load_bytes` (меньше вызовов helper’а на пакет).
- **Поведение при ошибке:** если линейная часть пакета короче 92 байт — сразу `return 1`, событие не шлётся. Нет «тихого» нулевого payload, как при неудачном load_bytes.

**Минусы / нюансы:**
- **Только linear part skb:** `data`..`data_end` — это линейный буфер. Если UDP-пакет в frags (редко для типичного DNS), мы можем не увидеть 92 байта и отбросить пакет. Для DNS over UDP пакеты обычно маленькие и в linear — на практике ОК.
- **IPv6 по-прежнему не поддерживается:** offset 28 зашит под IPv4. Для IPv6 нужна ветка с offset 48 и своей проверкой длины (см. E2).

**Нужен ли гибрид (часть через direct, часть через load_bytes)?** Для текущей задачи — **нет**. Прямого доступа достаточно: одна проверка на 92 байта (или на 112 при добавлении IPv6), затем только чтения по указателям. Гибрид имел бы смысл, если бы мы читали большой объём за пределами linear (тогда `bpf_skb_load_bytes` может тянуть из frags), но при 64 байтах payload и типичном DNS это не требуется.

**Итог:** подход корректен, компилируется и работает; для ВКР можно кратко описать выбор (direct access, одна bounds check, только linear part, IPv4-only) и при необходимости добавить IPv6 в том же стиле.

### 5.5 Два невалидированных детектора

C2_BEACON и HIGH_RATE не сработали ни разу. Это не баг — возможно, тестовые атаки не попали в их диапазон. Но для ВКР это значит, что 2 из 11 эвристик не подтверждены экспериментально. Стоит:
- Либо подобрать attack tool, который их триггерит
- Либо честно написать: «не все эвристики были задействованы в экспериментах»

## 7. Резюме

Проект **значительно дальше, чем «непроверенный прототип»**. Валидация проведена на реальном кластере с тремя attack tools и baseline. Ключевые результаты:

- **Детекция работает.** По распарсенным событиям Precision=1.0 для всех трёх tools. Real FPR=0.005%.
- **Ограничения понятны и описаны:** IPv6/unparseable (36% FN iodine), 64B payload (40% FN exfil), CoreDNS transit (артефакт GT).
- **Detection latency = 0.01 с** — отличный результат.

Главные открытые вопросы для ВКР:
1. Скорректированные метрики (разметка по домену) — **нужно реализовать, данные есть**
2. C2_BEACON и HIGH_RATE не валидированы — **нужно объяснить или найти tool, который триггерит**
3. CNI-agnostic — **не подтверждено на 2+ CNI**
4. Сравнение с альтернативами — **отсутствует**

Объём проделанной работы достаточен для магистерской ВКР при условии честного описания ограничений и артефактов.
