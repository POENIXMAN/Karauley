# Результаты валидации и обнаружения (2026-03)

Документ фиксирует **результаты первого прогона валидации** (Фаза B, iodine), **интерпретацию метрик**, **выявленные артефакты** и **идеи по расширению работ**.

---

## 1. Достаточно ли этого для диссертации (ВКР)?

**Кратко: да, при условии честного описания ограничений и интерпретации.**

### Что уже есть для ВКР

| Требование ВКР | Статус |
|---------------|--------|
| CNI-agnostic модуль на eBPF (cgroup_skb) | ✓ Реализован, работает |
| Атрибуция до пода (cgroup_id → pod) | ✓ Работает |
| Детекция DNS-туннелей (C2, Exfil, IP-over-DNS) | ✓ 10 из 11 эвристик работают |
| Экспериментальная оценка (confusion matrix, метрики) | ✓ Стенд есть, первый прогон (iodine) проведён |
| Интерпретируемые причины срабатывания | ✓ MANY_SUBDOMAINS, NULL_RECORD и др. |
| Низкая задержка детекции | ✓ 0.01 с (измерено) |

### Что нужно явно описать в тексте

1. **Ограничения eBPF-захвата:** только UDP/IPv4, payload 64 байта, DNS-запросы (query) часто дают `<unparseable>` (IPv6 / неудачное чтение skb). В диссертации — раздел «Ограничения» и «Рекомендации по развитию».
2. **Методология ground truth:** разметка по namespace пода даёт артефактные FP на транзитных компонентах (CoreDNS). Описать и при необходимости скорректировать метрики (разметка по домену или исключение транзитных подов).
3. **Скорректированные метрики:** для iodine по распарсенным ответам — Precision=1, Recall=1; сырые цифры занижены из-за артефактов. Таблицу в ВКР сопроводить пояснением.

**Вывод:** объёма и уровня проработки достаточно для магистерской ВКР. Инструмент в текущем виде демонстрирует работоспособность подхода; ограничения и артефакты — нормальная часть экспериментальной части при условии их явного описания.

## 2. Полезность инструмента в текущем состоянии

| Аспект | Оценка | Пояснение |
|--------|--------|-----------|
| **Детекция по ответам (response)** | **Высокая** | Каждый распарсенный DNS-ответ с признаками туннеля (NULL, длинные поддомены, rate) обнаруживается; задержка ~0.01 с. |
| **Детекция по запросам (query)** | **Ограничена** | Много событий с `<unparseable>` из-за IPv6 и формата захвата; запросы не всегда парсятся. |
| **Покрытие сценариев** | **Хорошее** | Iodine (IP-over-DNS) проверен; dnscat2 и DNSExfiltrator — в плане. Три типа туннелей (C2, Exfil, IP-over-DNS) покрыты эвристиками. |
| **Готовность к production** | **PoC / тестовый стенд** | Нет алертинга из коробки, нет пагинации K8s API, cardinality метрик не ограничена. Подходит для пилотов и экспериментов. |
| **Ценность для ВКР** | **Высокая** | Доказывает возможность CNI-agnostic детекции DNS-туннелей с атрибуцией до пода; даёт воспроизводимые эксперименты и метрики. |

**Итог:** инструмент **полезен** как прототип и основа для экспериментов. В текущем виде пригоден для обнаружения туннельного трафика по DNS-ответам в кластере; развитие (IPv6, парсинг query, тюнинг метрик) повысит полноту и пригодность для эксплуатации.

## 3. Результаты прогона iodine (Фаза B) — кратко

- **Сырые метрики:** TP=591, FN=2174, FP=590, TN=2641 → Precision≈0.50, Recall≈0.21, F1≈0.30, FPR≈18%.
- **Интерпретация:**
  - **FN=2174** — все с `domain="<unparseable>"`. eBPF не извлекает домен из DNS-запросов (query); это ограничение захвата, а не логики детектора.
  - **FP=590** — ответы, перехваченные на **CoreDNS** (kube-system). Трафик тот же туннельный; детектор верно помечает его, но разметка по namespace считает CoreDNS «легитимным» → алерты считаются FP.
- **Скорректированная интерпретация:** по распарсенным событиям и при учёте транзитного трафика как атаки — Precision=1, Recall=1, FPR=0; Detection Latency=0.01 с.
- **Детектор:** срабатывают MANY_SUBDOMAINS(50) и NULL_RECORD(iodine); threat_type=EXFIL+TUNNEL.

Подробности и формулы — в переписке/отчёте по эксперименту; здесь зафиксированы выводы для плана и документации.

## 4. Новые обнаружения (технические)

### 4.1 eBPF: парсинг только для части пакетов

- **Факт:** В логах много событий с `domain="<unparseable>"`, `direction="query"`, `dns_type=1`. Ответы (response) с теми же признаками туннеля парсятся и детектируются.
- **Причина:** В `dns_cgroup.bpf.c` DNS payload читается с **фиксированного offset 28** (IPv4: 20 байт IP + 8 байт UDP). Для **IPv6** заголовок 40 байт → DNS payload с offset 48; чтение с 28 даёт мусор или нули. Возврат `bpf_skb_load_bytes` не проверяется — при неудачном чтении payload остаётся нулевым → парсер выдаёт пустой домен → `<unparseable>`.
- **Следствие:** Запросы (query) часто не парсятся; ответы (response) в большинстве случаев парсятся (часто идут по IPv4). Туннельные инструменты генерируют много запросов → доля `<unparseable>` у них выше, чем у обычного трафика.
- **Где фиксировать:** LLM_CONTEXT.md (ограничения BPF), WORK_PLAN.md (задачи по улучшению).

### 4.2 Методология ground truth в analyze.py

- **Факт:** События от подов в `attack` и `attack-server` помечаются как attack; от `kube-system` (в т.ч. CoreDNS) — как legit. Туннельный трафик проходит через CoreDNS → алерты на CoreDNS считаются FP.
- **Следствие:** Занижение Precision и завышение FPR при разметке «по поду». Для корректной оценки можно: (A) размечать по домену (`*.attack.test` → attack), или (B) исключать транзитные поды (CoreDNS, attack-server) из подсчёта FP/FN.
- **Где фиксировать:** TESTING_PLAN.md (раздел ground truth), опционально — режим в analyze.py (--gt-by-domain или --exclude-transit).

### 4.3 In-cluster серверы (attack-server)

- Стенд использует серверы туннелей **внутри кластера** (namespace `attack-server`), CoreDNS форвардит `attack.test` на ClusterIP. Схема рабочая; трафик виден монитору на всех этапах (клиент → CoreDNS → сервер), что усиливает артефакт «один обмен = много событий с разных подов».

## 5. Рекомендации по расширению плана работ

### 5.1 Обязательно для качественной ВКР

| Задача | Описание | Оценка |
|--------|----------|--------|
| Прогоны dnscat2 и DNSExfiltrator (Фаза B, при необходимости C) | Заполнить таблицу метрик по всем трём инструментам | 4–6 ч |
| Раздел «Ограничения» в тексте ВКР | eBPF: IPv4, 64 B, unparseable query; методология GT по поду | 1–2 ч |
| Таблица метрик с пояснением | Сырые + скорректированные (или только по parseable) для iodine; описание артефактов | 1 ч |

### 5.2 Улучшения (укрепляют выводы и будущее использование)

| Задача | Описание | Оценка |
|--------|----------|--------|
| eBPF: проверка возврата `bpf_skb_load_bytes` | Не слать событие при неудачном чтении; снизить шум `<unparseable>` | 1–2 ч |
| eBPF: поддержка IPv6 | Определять версию IP (по полю version), брать payload с offset 28 (IPv4) или 48 (IPv6) | 4–8 ч |
| analyze.py: опция разметки по домену | `--gt-by-domain`: `*.attack.test` → attack; убрать артефакт FP на CoreDNS | 2–3 ч |
| analyze.py: исключение транзитных подов | Не считать события от `kube-system/coredns` и опционально `attack-server/*` в FP/FN | 1–2 ч |

### 5.3 Опционально (перспектива развития)

| Задача | Описание |
|--------|----------|
| Увеличение payload (если окружение стабильно) | Проверка на тестовом ядре: PAYLOAD_SAMPLE 128/256 для длинных доменов и LONG_DOMAIN |
| TCP DNS (порт 53) | Отдельный хук для TCP; парсинг DNS поверх TCP для полноты |
| ROC-кривые и чувствительность к порогу | Зависимость Precision/Recall от score threshold для раздела «Эксперименты» |
