# Анализ TCP DNS части: Проблемы и решения

## Отзыв: Основные моменты

### ✅ Что работает хорошо:

1. **Стандартный length-prefix (2 байта)** - корректно для DNS-over-TCP
2. **Проверка диапазона dns_len (12-512)** - защита от мусора
3. **Fast-path в kprobe** - пытаемся сразу прочитать, если не получилось - в kretprobe
4. **Fallback логика** - повторное чтение из msg->msg_iter в kretprobe

### ⚠️ Основные проблемы:

1. **Фрагментация DNS по TCP-потоку**
2. **Использование data_ptr в kretprobe** (может быть невалидным)
3. **Дублирование логики** между kprobe и kretprobe
4. **Best-effort подход** (не гарантированный детект)

---

## Проблема 1: Фрагментация DNS по TCP-потоку

### Что это значит?

**DNS-over-TCP формат:**
```
[2 байта: длина][DNS payload]
```

**Проблема**: TCP может разбить данные на несколько `sendmsg`/`recvmsg` вызовов:

```
Вызов 1: [0x00 0x32]  ← только length-prefix (2 байта)
Вызов 2: [DNS header][Question]... ← только payload
```

Или наоборот:
```
Вызов 1: [0x00 0x32][DNS header] ← length-prefix + часть payload
Вызов 2: [Question][Answer]... ← остаток payload
```

### Что происходит в нашем коде?

**Текущая логика:**
```c
// В kprobe__tcp_sendmsg:
u8 tcp_header[2];
bpf_probe_read_user(tcp_header, 2, data_ptr);  // Читаем length-prefix
u16 dns_len = (tcp_header[0] << 8) | tcp_header[1];

if (dns_len >= 12 && dns_len <= 512) {
    // Читаем DNS данные
    bpf_probe_read_user(event.dns_data, dns_len, data_ptr + 2);
}
```

**Проблема**: Если `data_ptr` указывает на середину пакета (не на начало length-prefix), то:
- `tcp_header[2]` читает мусор
- `dns_len` получается невалидным
- Мы либо дропаем событие, либо читаем "левые" данные

### Пример проблемы:

```
TCP поток:
  [0x00 0x32][DNS header][Question]...

Вызов 1 (kprobe__tcp_sendmsg):
  data_ptr → указывает на [0x00 0x32]
  Читаем: tcp_header = [0x00, 0x32] ✅
  dns_len = 50 ✅
  Читаем: event.dns_data = [DNS header][Question]... ✅
  Работает!

Вызов 2 (если данные фрагментированы):
  data_ptr → указывает на [Question]... (середина пакета)
  Читаем: tcp_header = [0x??, 0x??] ❌ (мусор!)
  dns_len = случайное число ❌
  Если dns_len в диапазоне 12-512, читаем мусор ❌
```

### Решение:

**Вариант 1: Принять best-effort подход** (текущий)
- Детектируем только когда данные попали в один вызов
- Для фрагментированных пакетов - пропускаем
- Основной фокус на UDP (где нет фрагментации)

**Вариант 2: Reassembly в userspace** (сложнее)
- В eBPF только отмечаем начало/конец сегментов
- В userspace собираем полный пакет
- Сложно и не нужно для туннелей (UDP достаточно)

**Рекомендация**: Оставить best-effort, но добавить комментарий.

## Проблема 2: Использование data_ptr в kretprobe

### Что это значит?

**Текущая логика:**
```c
// В kprobe__tcp_sendmsg:
sctx.data_ptr = data_ptr;  // Сохраняем указатель

// В kretprobe__tcp_sendmsg:
void *data_ptr = sctx->data_ptr;  // Используем сохраненный указатель
bpf_probe_read_user(event.dns_data, MAX_DNS_DATA, data_ptr);
```

**Проблема**: К моменту `kretprobe`:
- Userspace может уже переиспользовать буфер
- Буфер может быть освобожден
- `data_ptr` может указывать на невалидные данные

### Почему это работает на практике?

1. **Буфер обычно живет дольше** - между kprobe и kretprobe проходит мало времени
2. **TCP буферы не освобождаются сразу** - ядро держит их до отправки
3. **Но формально это не гарантировано**

### Что у нас уже есть (fallback):

```c
// В kretprobe__tcp_sendmsg:
// Сначала пробуем из сохраненного указателя
if (data_ptr) {
    // ... чтение из data_ptr
}

// Если не получилось, пробуем из msg->msg_iter
if (!data_read && sctx->msg) {
    struct iov_iter iter;
    bpf_probe_read_kernel(&iter, sizeof(iter), &sctx->msg->msg_iter);
    void *new_data_ptr = get_data_ptr_from_iter(&iter);
    // ... чтение из new_data_ptr
}
```

**Это хорошо!** Но нужно понимать, что это best-effort.

## Проблема 3: Дублирование логики

### Что это значит?

**Текущая ситуация:**
- В `kprobe__tcp_sendmsg` есть блок чтения length-prefix и payload
- В `kretprobe__tcp_sendmsg` есть **почти идентичный** блок
- Код дублируется, увеличивая размер eBPF программы

**Пример дублирования:**
```c
// В kprobe__tcp_sendmsg:
u8 tcp_header[2];
bpf_probe_read_user(tcp_header, 2, data_ptr);
u16 dns_len = (tcp_header[0] << 8) | tcp_header[1];
if (dns_len >= 12 && dns_len <= 512) {
    bpf_probe_read_user(event.dns_data, dns_len, data_ptr + 2);
    parse_dns_header(event.dns_data, event.data_len, &event);
}

// В kretprobe__tcp_sendmsg:
u8 tcp_header[2];  // ДУБЛИРОВАНИЕ
bpf_probe_read_user(tcp_header, 2, data_ptr);  // ДУБЛИРОВАНИЕ
u16 dns_len = (tcp_header[0] << 8) | tcp_header[1];  // ДУБЛИРОВАНИЕ
if (dns_len >= 12 && dns_len <= 512) {  // ДУБЛИРОВАНИЕ
    bpf_probe_read_user(event.dns_data, dns_len, data_ptr + 2);  // ДУБЛИРОВАНИЕ
    parse_dns_header(event.dns_data, event.data_len, &event);  // ДУБЛИРОВАНИЕ
}
```

### Решение:

**Вынести в функцию:**
```c
static __always_inline int read_dns_from_tcp(void *data_ptr, struct dns_event *event) {
    if (!data_ptr) {
        return 0;
    }
    
    // Читаем length-prefix
    u8 tcp_header[2];
    long ret = bpf_probe_read_user(tcp_header, 2, data_ptr);
    if (ret != 0) {
        return 0;
    }
    
    u16 dns_len = (tcp_header[0] << 8) | tcp_header[1];
    
    // Проверяем валидность
    if (dns_len < 12 || dns_len > 512) {
        return 0;
    }
    
    // Читаем DNS данные
    u16 read_len = dns_len < MAX_DNS_DATA ? dns_len : MAX_DNS_DATA;
    ret = bpf_probe_read_user(event->dns_data, read_len, data_ptr + 2);
    if (ret != 0) {
        return 0;
    }
    
    event->data_len = read_len;
    parse_dns_header(event->dns_data, event->data_len, event);
    return 1;
}
```

**Использовать в обоих местах:**
```c
// В kprobe__tcp_sendmsg:
if (read_dns_from_tcp(data_ptr, &event)) {
    events.ringbuf_output(&event, sizeof(event), 0);
    return 0;
}

// В kretprobe__tcp_sendmsg:
if (read_dns_from_tcp(data_ptr, &event)) {
    data_read = 1;
}
```

**Плюсы**:
- Убирает дублирование
- Упрощает поддержку
- Меньше кода для верификатора

## Проблема 4: Best-effort подход

### Что это значит?

**Текущая реализация:**
- Не гарантирует детект всех TCP DNS пакетов
- Работает только когда данные попали в один вызов
- Фрагментированные пакеты могут быть пропущены

### Это проблема?

**Для детекции туннелей - НЕТ!**

**Почему:**
1. **UDP - основной канал туннелей**
   - Большинство DNS туннелей используют UDP
   - TCP используется реже (обычно для больших ответов)
   - UDP детектируется надежно (нет фрагментации)

2. **TCP - дополнительный сигнал**
   - Если TCP пакет попал целиком - детектируем
   - Если фрагментирован - не критично (UDP покрывает)

3. **Статистика важнее payload**
   - Частота запросов
   - Длины доменов
   - Типы записей
   - Это работает и для TCP (даже без полного payload)

### Рекомендация:

**Принять best-effort подход**, но:
1. Добавить комментарий в код
2. В userspace обрабатывать `data_len == 0` для TCP
3. Фокус на UDP для основного детекта

## Рекомендации по улучшению

### Минимальные улучшения (без изменения логики):

1. **Добавить комментарий о best-effort:**
```c
// TCP DNS handling: best-effort approach
// 
// DNS-over-TCP может быть фрагментирован по нескольким sendmsg/recvmsg вызовам.
// Мы детектируем только случаи, когда length-prefix и payload попали в один вызов.
// Для фрагментированных пакетов событие может быть пропущено или иметь data_len=0.
//
// Это приемлемо для детекции туннелей, так как:
// - UDP является основным каналом туннелей (детектируется надежно)
// - TCP используется реже и служит дополнительным сигналом
// - Статистика (частота, длины) работает даже без полного payload
```

2. **Вынести чтение TCP в функцию** (убрать дублирование)

3. **В userspace обрабатывать data_len==0:**
```python
# В handle_event:
if event.protocol == 6 and event.data_len == 0:  # TCP без данных
    # Используем как сигнал существования TCP DNS (без payload анализа)
    # Основной детект полагается на UDP
    pass
```

### Более серьезные улучшения (если нужно):

1. **Reassembly в userspace** (сложно, не нужно для туннелей)
2. **Только статистика для TCP** (без payload, только метаданные)
