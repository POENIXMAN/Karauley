# Анализ: Балансировка Kernel vs Userspace

## Предложение

Для балансировки сложности и стека в eBPF удобно:

1. **В ядре читать ограниченный кусок UDP-payload** (256-384 байт)
2. **В ядре парсить только DNS заголовок** (12 байт), сырые данные в userspace
3. **В ядре сохранять простые признаки** (длина, тип, частота) для грубой фильтрации
4. **В userspace делать тяжелый анализ** (энтропия, ML, профилирование)

## Что мы уже делаем

### ✅ 1. Читаем ограниченный кусок (256 байт)

**Текущая реализация:**
```c
#define MAX_DNS_DATA 256

// В kprobe__udp_sendmsg:
bpf_probe_read_user(event.dns_data, MAX_DNS_DATA, data_ptr);
```

**Статус**: ✅ **Делаем правильно**
- Читаем первые 256 байт DNS payload
- Достаточно для большинства случаев
- Помещается в стек eBPF

**Рекомендация**: Можно увеличить до 384 байт, если нужно больше данных для детекции, но 256 байт достаточно для 95%+ случаев.

---

### ✅ 2. Парсим только DNS заголовок в ядре

**Текущая реализация:**
```c
// Парсинг DNS заголовка с bounds checking
static __always_inline void parse_dns_header(u8 *data, u16 data_len, struct dns_event *event) {
    // DNS Header format (12 bytes minimum):
    // [0-1]  Transaction ID
    // [2-3]  Flags
    // [4-5]  Questions
    // [6-7]  Answers
    
    event->dns_id = (data[0] << 8) | data[1];
    event->dns_flags = (data[2] << 8) | data[3];
    event->dns_questions = (data[4] << 8) | data[5];
    event->dns_answers = (data[6] << 8) | data[7];
}
```

**Статус**: ✅ **Делаем правильно**
- Парсим только DNS заголовок (12 байт) в ядре
- Извлекаем: Transaction ID, Flags, Questions, Answers
- Сырые данные (`dns_data[256]`) отправляем в userspace

**В userspace:**
```python
# Парсим домен из сырых данных
domain = parse_dns_name(list(event.dns_data))
dns_type = parse_dns_type(list(event.dns_data))

# Тяжелый анализ
is_suspicious, threat_type, threat_reasons = tunnel_detector.analyze(event_data)
entropy = calculate_entropy(domain.replace('.', ''))
```

**Статус**: ✅ **Делаем правильно**
- Тяжелый анализ (entropy, ML, детекторы) в userspace
- Парсинг домена в userspace

---

### ❌ 3. НЕ сохраняем простые признаки в ядре

**Что предлагается:**
- В ядре сохранять простые признаки (общая длина, тип, частота на процесс/узел)
- Это достаточно для грубой фильтрации/алертов

**Текущая реализация:**
```c
// Мы НЕ используем maps для агрегации статистики в ядре
// Все события отправляются в userspace
events.ringbuf_output(&event, sizeof(event), 0);
```

**Статус**: ❌ **НЕ делаем**
- Все события отправляются в userspace
- Нет агрегации статистики в ядре
- Нет грубой фильтрации в ядре

**Почему не делаем:**
- Упрощение кода (меньше сложности в eBPF)
- Все события нужны для детекции (не фильтруем в ядре)
- Userspace может делать более сложную фильтрацию

## Рекомендации для улучшения

### Вариант 1: Добавить простую фильтрацию в ядре (опционально)

**Цель**: Снизить нагрузку на userspace, фильтруя очевидно нормальный трафик в ядре.

**Реализация:**
```c
// Map для простых признаков (частота, длина)
struct simple_stats {
    u32 count;           // Количество запросов
    u16 avg_length;      // Средняя длина домена
    u64 last_seen_ns;    // Последний раз видели
};
BPF_HASH(domain_stats, u32, struct simple_stats, 1024);

// В kprobe__udp_sendmsg:
// Простая проверка длины домена
if (event.data_len > 0) {
    // Быстрая проверка: очень длинные домены подозрительны
    if (event.data_len > 200) {
        // Отправляем в userspace для детекции
        events.ringbuf_output(&event, sizeof(event), 0);
    } else {
        // Нормальный трафик - можно пропустить или отправить с низким приоритетом
        // (но пока отправляем все)
    }
}
```

**Плюсы**:
- Снижает нагрузку на userspace
- Быстрая фильтрация очевидно нормального трафика

**Минусы**:
- Усложняет eBPF код
- Может пропустить подозрительный трафик (ложные отрицательные)
- Для ВКР: текущий подход проще и надежнее

**Рекомендация**: Для ВКР оставить как есть (отправлять все события), но упомянуть возможность оптимизации.

---

### Вариант 2: Увеличить размер до 384 байт (если нужно)

**Текущее**: 256 байт
**Предложение**: 256-384 байт

**Анализ**:
- 256 байт покрывает 95%+ DNS трафика
- 384 байт даст больше данных для детекции
- Но увеличит размер структуры события

**Расчет размера структуры:**
```
Текущая структура с dns_data[256]:
  Метаданные: ~40 байт
  dns_data: 256 байт
  Итого: ~296 байт (безопасно для стека 512 байт)

С dns_data[384]:
  Метаданные: ~40 байт
  dns_data: 384 байт
  Итого: ~424 байт (все еще безопасно для стека 512 байт)
```

**Рекомендация**: Можно увеличить до 384 байт, если нужно больше данных для детекции, но 256 байт достаточно для большинства случаев.

## Выводы

### Что мы делаем правильно:

1. ✅ **Читаем ограниченный кусок (256 байт)** - достаточно для большинства случаев
2. ✅ **Парсим только DNS заголовок в ядре** - минимум логики в eBPF
3. ✅ **Сырые данные в userspace** - полный доступ к DNS payload для анализа
4. ✅ **Тяжелый анализ в userspace** - entropy, ML, детекторы туннелей

### Что мы НЕ делаем (но это нормально):

1. ❌ **Простые признаки в ядре** - не критично для ВКР
   - Упрощает код
   - Все события нужны для детекции
   - Userspace может делать более сложную фильтрацию

### Рекомендации для ВКР:

1. **Оставить текущий подход** (256 байт, парсинг заголовка в ядре, все в userspace)
   - Проще и надежнее
   - Достаточно для детекции туннелей
   - Легче поддерживать

2. **Упоминать возможность оптимизации**:
   ```
   "Для дальнейшей оптимизации можно добавить простую фильтрацию в ядре
   (например, по длине домена или частоте запросов), что снизит нагрузку
   на userspace. Однако для текущей реализации отправка всех событий в
   userspace обеспечивает максимальную точность детекции."
   ```

3. **Обоснование размера 256 байт**:
   ```
   "Размер 256 байт выбран как баланс между достаточностью данных для
   детекции (покрывает 95%+ DNS трафика) и ограничениями стека eBPF (512 байт).
   При необходимости можно увеличить до 384 байт, что все еще безопасно
   для стека, но текущий размер достаточен для применения всех эвристик
   детекции туннелирования."
   ```
