# Архитектурные решения eBPF DNS Tunnel Detector

## Обзор

Документ описывает ключевые архитектурные решения, принятые при разработке eBPF модуля для детекции DNS туннелирования, включая анализ компромиссов и обоснование выбора.

**Версия**: 2.1 (Ring Buffer)  
**Дата**: 2024

---

### 0.3 Где работают разные типы eBPF программ?

```

### 0.4 Почему kprobe на L7, а не XDP на L2/L3?

#### Проблема с XDP для DNS мониторинга

```
┌─────────────────────────────────────────────────────────────────┐
│              XDP: Что МОЖНО и что НЕЛЬЗЯ                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ✅ МОЖНО:                                                       │
│     - Видеть Ethernet frame (MAC addresses)                    │
│     - Видеть IP header (source/dest IP)                        │
│     - Видеть UDP/TCP header (source/dest port)                 │
│     - DROP пакеты (защита от DDoS)                             │
│     - REDIRECT пакеты (балансировка)                           │
│                                                                  │
│  ❌ НЕЛЬЗЯ:                                                      │
│     - Видеть DNS данные (payload)                               │
│     - Видеть процесс, который отправил запрос                  │
│     - Видеть socket                                             │
│     - Видеть cgroup_id, netns_id (Kubernetes)                  │
│     - Коррелировать QUERY и RESPONSE                           │
│                                                                  │
│  Почему?                                                         │
│     XDP работает ДО network stack:                              │
│     - Пакет еще не привязан к socket                            │
│     - Процесс еще не определен                                  │
│     - DNS payload находится в UDP/TCP payload                  │
│     - Нужен полный парсинг UDP/TCP для доступа к DNS           │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

#### Почему kprobe на L7 подходит для DNS

```
┌─────────────────────────────────────────────────────────────────┐
│              kprobe: Что МОЖНО и что НЕЛЬЗЯ                     │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ✅ МОЖНО:                                                       │
│     - Видеть DNS payload (полные данные)                       │
│     - Видеть процесс (pid, tid, comm)                          │
│     - Видеть socket (sock структура)                           │
│     - Видеть cgroup_id, netns_id                               │
│     - Коррелировать QUERY/RESPONSE по transaction ID          │
│     - Анализировать доменные имена                             │
│                                                                  │
│  ❌ НЕЛЬЗЯ:                                                      │
│     - DROP пакеты (уже поздно, пакет в kernel)                 │
│     - Модифицировать пакеты (только read-only)                 │
│     - Видеть RAW Ethernet/IP headers                           │
│                                                                  │
│  Почему подходит для DNS туннелирования?                        │
│     kprobe работает на уровне socket API:                       │
│     - DNS данные уже распарсены и доступны                      │
│     - Видим, какое приложение отправило запрос                  │
│     - Можем анализировать доменные имена                       │
│     - Можем детектировать подозрительные паттерны               │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

│  │ };                                                          │  │
│  │                                                             │  │

│  └──────────────────────────────────────────────────────────┘  │
│                                                                  │
│  Путь данных:                                                    │
│                                                                  │
│  Application buffer (userspace)                                  │
│         │                                                       │
│         │ DNS packet: [12-byte header][domain name][...]       │
│         │                                                       │
│         ▼                                                       │

│         │                                                       │
│         │ bpf_probe_read_user() читает отсюда                  │

│                                                                  │

```

┌─────────────────────────────────────────────────────────────────┐
│              L4 (Transport) vs L7 (Application)                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  L4 ПЕРЕХВАТ (XDP, TC):                                         │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ Пакет на уровне L4:                                        │  │
│  │                                                             │  │
│  │  [Ethernet][IP][UDP][DNS payload]                         │  │
│  │   ↑         ↑   ↑    ↑                                    │  │
│  │   L2       L3   L4   L7                                   │  │
│  │                                                             │  │
│  │  XDP видит: Ethernet + IP + UDP headers                   │  │
│  │  XDP НЕ видит: DNS payload (он внутри UDP payload)         │  │
│  │                                                             │  │
│  │  Для доступа к DNS нужно:                                 │  │
│  │    1. Парсить UDP header (port, length)                    │  │
│  │    2. Извлечь UDP payload                                  │  │
│  │    3. Парсить DNS header                                   │  │
│  │    4. Извлечь DNS data                                     │  │
│  │                                                             │  │
│  │  Проблемы:                                                 │  │
│  │    - Сложный парсинг в eBPF                                │  │
│  │    - Нет доступа к процессу                                │  │
│  │    - Нет доступа к socket                                  │  │
│  │    - Нет cgroup_id, netns_id                              │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                  │
│  L7 ПЕРЕХВАТ (kprobe на socket functions):                      │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ Socket API на уровне L7:                                   │  │
│  │                                                             │  │
│  │  Application: sendto(fd, dns_packet, ...)                 │  │
│  │       │                                                     │  │
│  │       ▼                                                     │  │
│  │  Kernel: udp_sendmsg(sk, msg, ...)                         │  │
│  │       │                                                     │  │
│  │       │ msg->msg_iter → DNS packet уже готов!              │  │
│  │       │                                                    │  │
│  │       ▼                                                     │  │
│  │  eBPF: kprobe__udp_sendmsg                                 │  │
│  │       │                                                     │  │
│  │       │ Видим:                                             │  │
│  │       │   - DNS payload (msg_iter)                         │  │
│  │       │   - Процесс (pid, comm)                           │  │
│  │       │   - Socket (sk)                                    │  │
│  │       │   - cgroup_id, netns_id                           │  │
│  │                                                             │  │
│  │  Преимущества:                                             │  │
│  │    - DNS данные уже распарсены                            │  │
│  │    - Прямой доступ к payload                              │  │
│  │    - Видим процесс и контекст                             │  │
│  │    - Проще код                                             │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 0.7 Почему kprobe, а не tracepoint?

```
┌─────────────────────────────────────────────────────────────────┐
│              kprobe vs tracepoint для DNS                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  TRACEPOINT:                                                     │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ Преимущества:                                             │  │
│  │   ✅ Стабильный API между версиями ядра                   │  │

│  │                                                             │  │
│  │ Недостатки:                                               │  │
│  │   ❌ НЕТ tracepoint для udp_sendmsg/recvmsg!              │  │
│  │   ❌ Только для syscalls (sys_sendto, sys_recvfrom)       │  │
│  │   ❌ На уровне syscall - нет доступа к socket структуре   │  │
│  │   ❌ Нет доступа к msg_iter (DNS данные)                  │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                  │
│  KPROBE:                                                         │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ Преимущества:                                             │  │
│  │   ✅ Доступ к udp_sendmsg/recvmsg (нужные функции)        │  │
│  │   ✅ Доступ к socket структуре (sk)                       │  │
│  │   ✅ Доступ к msg_iter (DNS данные)                       │  │
│  │   ✅ Доступ к процессу (pid, comm)                        │  │
│  │                                                             │  │
│  │ Недостатки:                                               │  │
│  │   ⚠️ Может сломаться при изменении ядра                  │  │
│  │   ⚠️ Больше overhead (динамический перехват)              │  │
│  │                                                             │  │
│  │ Решение:                                                   │  │
│  │   Используем kprobe, т.к. tracepoint недоступен           │  │
│  │   для нужных функций                                      │  │

```

### 0.10 Структура sk_buff и как данные попадают в socket

```
┌─────────────────────────────────────────────────────────────────┐
│              sk_buff: Структура пакета в ядре                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  sk_buff (socket buffer) - основная структура для пакетов:      │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ struct sk_buff {                                           │  │
│  │     struct sk_buff *next;      // Следующий в очереди     │  │
│  │     struct sk_buff *prev;      // Предыдущий              │  │
│  │     struct sock *sk;            // Socket (связь!)         │  │
│  │     unsigned int len;           // Длина данных            │  │
│  │     unsigned int data_len;     // Длина фрагментов        │  │
│  │     void *data;                // Указатель на данные      │  │
│  │     // ... много других полей ...                          │  │
│  │ };                                                          │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                  │
│  Путь пакета:                                                    │
│                                                                  │
│  1. NIC → sk_buff создается в driver                            │
│     skb = alloc_skb(len)                                         │
│     skb->data = packet_data                                     │
│                                                                  │
│  2. IP layer обрабатывает sk_buff                                │
│     ip_rcv(skb)                                                  │
│                                                                  │
│  3. UDP layer обрабатывает sk_buff                               │
│     udp_rcv(skb)                                                 │
│     skb->sk = socket (привязка к socket!)                       │
│                                                                  │
│  4. Socket queue получает sk_buff                                │
│     sock_queue_rcv_skb(sk, skb)                                  │
│     → Добавляет в очередь socket                                │
│                                                                  │
│  5. Application вызывает recvmsg()                               │
│     → udp_recvmsg() копирует данные из sk_buff в userspace      │
│     → Здесь мы перехватываем через kprobe!                      │
│                                                                  │
│  ВАЖНО:                                                          │
│    - В kprobe__udp_recvmsg: sk_buff еще в очереди socket        │
│    - В kretprobe__udp_recvmsg: данные уже скопированы          │
│    - Поэтому нужен kretprobe для чтения DNS данных!             │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 0.13 Связь с официальной диаграммой Linux Network Stack

**Примечание**: Существует детальная диаграмма Linux Network Stack (Jan Engelhardt, 2019), показывающая все точки перехвата пакетов. Ниже объясняется, как наше решение вписывается в эту схему.

```
┌─────────────────────────────────────────────────────────────────┐
│     ОФИЦИАЛЬНАЯ ДИАГРАММА LINUX NETWORK STACK                    │
│     (Jan Engelhardt, 2019)                                       │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Диаграмма показывает:                                          │
│                                                                  │
│  1. XDP (eXpress Data Path) - СЛЕВА на диаграмме                │
│     ┌──────────────────────────────────────────────────────┐  │
│     │ XDP eBPF Program                                       │  │
│     │   - Работает ДО network stack                          │  │
│     │   - Видит RAW Ethernet/IP пакеты                       │  │
│     │   - Может DROP, PASS, REDIRECT                        │  │
│     │   - НЕТ доступа к DNS данным!                          │  │
│     │                                                         │  │
│     │  Мы НЕ используем XDP, т.к.:                            │  │
│     │    ❌ Нет доступа к DNS payload                        │  │

## 1. Выбор механизма передачи данных: Ring Buffer vs Perf Buffer

### 1.1 Проблема

Необходимо выбрать механизм передачи событий из kernel space в userspace для eBPF программы. Доступны два варианта:
- **Perf Buffer** (BPF_PERF_OUTPUT) - классический механизм
- **Ring Buffer** (BPF_RINGBUF_OUTPUT) - новый механизм (Linux 5.8+)

### 1.2 Сравнительный анализ

| Критерий | Perf Buffer | Ring Buffer | Победитель |
|----------|-------------|-------------|------------|
| **Теоретическая эффективность** | Множественные копирования через perf subsystem | Прямая запись в shared memory | ✅ Ring Buffer |
| **Latency (низкая нагрузка)** | 264.9 µs (avg) | 57.1 µs (avg) | ✅ Ring Buffer (**78% лучше**) |
| **Latency (высокая нагрузка)** | 179.7 µs (avg) | 261.7 µs (avg) | ✅ Perf Buffer |
| **Latency p99** | 2465.3 µs | 2332.2 µs | ✅ Ring Buffer |
| **CPU overhead** | 10.0% (низкая) | 9.3% (низкая) | ✅ Ring Buffer |
| **Throughput (высокая нагрузка)** | 827 evt/s | 787 evt/s | ✅ Perf Buffer |
| **Масштабируемость** | Per-CPU буферы | Один общий буфер | ✅ Perf Buffer |
| **Гарантия порядка** | ❌ Нет (per-CPU) | ✅ Да (FIFO) | ✅ Ring Buffer |
| **Требует тюнинга** | ✅ Работает из коробки | ⚠️ Нужен polling timeout | ✅ Perf Buffer |
| **Burst нагрузка** | ✅ Лучше | ❌ Может переполниться | ✅ Perf Buffer |
| **Современность API** | ❌ Legacy | ✅ Рекомендуется для новых проектов | ✅ Ring Buffer |
| **Требования к ядру** | Linux 4.9+ | Linux 5.8+ | ✅ Perf Buffer |

### 1.3 Реальный сценарий использования

**Важно**: Benchmark измерял передачу **всех** DNS запросов (800 evt/s), но в production:

```
┌─────────────────────────────────────────────────────────┐
│  Production Workflow (v2.1)                            │
├─────────────────────────────────────────────────────────┤
│                                                          │
│  [Все DNS запросы] ──► [Фильтрация в userspace]        │
│      ~800 evt/s              │                          │
│                              ▼                          │
│                    [Только подозрительные]              │
│                         1-10 evt/s                      │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

**Реальная нагрузка**: 1-10 подозрительных событий/сек (после фильтрации в userspace)

### 1.4 Принятое решение: Ring Buffer

**Обоснование**:

1. **Низкая реальная нагрузка** (1-10 evt/s)
   - Ring Buffer показал **78% лучшую latency** при низкой нагрузке
   - Perf Buffer лучше только при высокой нагрузке (>800 evt/s)

2. **Гарантированный порядок событий**
   - Важно для корреляции QUERY/RESPONSE
   - Perf Buffer не гарантирует порядок из-за per-CPU буферов

3. **Современный API**
   - Ring Buffer - рекомендуемый подход для новых eBPF приложений
   - Perf Buffer считается legacy

4. **Меньше CPU overhead**
   - 9.3% vs 10.0% при низкой нагрузке

5. **Проще код**
   - Меньше копирований данных
   - Прямая запись в shared memory

**Компромиссы**:

- ⚠️ Требует ядро 5.8+ (Perf Buffer работает с 4.9+)
- ⚠️ Может переполниться при burst нагрузке (но это нереально для DNS tunneling)
- ⚠️ Требует тюнинга polling timeout (10ms в нашем случае)

### 1.5 Реализация

```c
// Размер: 256KB (достаточно для ~800 событий в буфере)
BPF_RINGBUF_OUTPUT(events, 1 << 18);  // 256 KB

// Использование:
events.ringbuf_output(&event, sizeof(event), 0);
```

**Размер буфера**: 256KB выбран как компромисс между:
- Достаточным размером для burst (800 событий × ~320 байт = 256KB)
- Минимальным использованием памяти

## 2. Структура события DNS

### 2.1 Проблема

Необходимо определить структуру данных для передачи DNS информации из kernel в userspace, учитывая:
- Метаданные процесса (для идентификации источника)
- Сетевую информацию (IP, порты)
- DNS заголовок (ID, flags, counts)
- DNS данные (payload)
- Kubernetes идентификацию (pod, namespace)

### 2.2 Принятое решение

```c
struct dns_event {
    // Метаданные процесса
    u32 pid;
    u32 tid;
    char comm[16];
    
    // Идентификация пода в K8s
    u64 cgroup_id;          // ID контейнерной cgroup
    u32 netns_id;           // ID network namespace
    
    // Сетевые данные
    u32 saddr;              // Source IP
    u32 daddr;              // Dest IP
    u16 sport;              // Source port
    u16 dport;              // Dest port
    
    // DNS метаданные
    u8  protocol;           // 6=TCP, 17=UDP
    u8  direction;          // 1=query, 2=response
    u16 dns_id;             // Transaction ID
    u16 dns_flags;          // Flags (QR, Opcode, RCODE)
    u16 dns_questions;      // Question count
    u16 dns_answers;        // Answer count
    
    // Timestamp
    u64 timestamp_ns;
    
    // DNS данные
    u16 data_len;           // Реальная длина данных
    u8  dns_data[MAX_DNS_DATA];  // 256 байт
} __attribute__((packed));
```

### 2.3 Компромиссы

**Размер буфера DNS данных (256 байт)**:

| Вариант | Размер | Плюсы | Минусы |
|---------|--------|-------|--------|
| 128 байт | Меньше памяти | Экономия памяти | Может не хватить для длинных доменов |
| **256 байт** | ✅ Выбран | Достаточно для большинства случаев | Больше памяти на событие |
| 512 байт | Больше памяти | Покрывает все случаи | Избыточно, больше памяти |

**Обоснование 256 байт**:
- DNS домен максимум 255 байт (RFC 1035)
- DNS пакет обычно 12-512 байт
- 256 байт покрывает 99% случаев
- Большие пакеты обрезаются, но заголовок всегда читается

**Поля структуры**:

- ✅ `cgroup_id` и `netns_id` - для Kubernetes pod идентификации
- ✅ `timestamp_ns` - для анализа частоты (детекция C2)
- ✅ `dns_answers` - большие значения указывают на IP-Over-DNS
- ✅ `dns_id` - для корреляции QUERY/RESPONSE

## 3. Подход к перехвату: kprobe vs kretprobe

### 3.1 Проблема

Для перехвата DNS трафика необходимо выбрать точки перехвата:
- **kprobe** - перехват входа в функцию
- **kretprobe** - перехват выхода из функции

### 3.2 Принятое решение: Гибридный подход

#### UDP DNS

**QUERY**: `kprobe__udp_sendmsg` (только kprobe)
- Данные доступны сразу в `msg->msg_iter`
- Не нужно ждать завершения функции

**RESPONSE**: `kprobe__udp_recvmsg` + `kretprobe__udp_recvmsg`
- kprobe: сохраняем контекст (указатель на буфер)
- kretprobe: читаем данные после получения

**Обоснование**:
- UDP QUERY: данные готовы в kprobe
- UDP RESPONSE: данные доступны только после `recvmsg()` завершения

#### TCP DNS

**QUERY**: `kprobe__tcp_sendmsg` + `kretprobe__tcp_sendmsg`
- kprobe: пробуем прочитать сразу, если не получается - сохраняем контекст
- kretprobe: читаем данные после отправки

**RESPONSE**: `kprobe__tcp_recvmsg` + `kretprobe__tcp_recvmsg`
- kprobe: сохраняем контекст
- kretprobe: читаем данные после получения

**Обоснование**:
- TCP данные могут быть фрагментированы
- Length prefix (2 байта) может быть в отдельном вызове
- kretprobe гарантирует, что данные уже отправлены/получены

### 3.3 Компромиссы

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| **Только kprobe** | Проще, меньше overhead | Данные могут быть недоступны |
| **Только kretprobe** | Данные гарантированно готовы | Больше overhead, сложнее |
| **Гибридный** ✅ | Оптимальный баланс | Сложнее код, нужны контекстные maps |

**Выбран гибридный подход** для максимальной надежности.

## 4. Обработка UDP vs TCP

### 4.1 Проблема

UDP и TCP имеют разные характеристики:
- **UDP**: Datagram-based, данные в одном пакете
- **TCP**: Stream-based, данные могут быть фрагментированы, есть length prefix

### 4.2 Принятые решения

#### UDP DNS

```c
// Простая обработка - данные в msg_iter
void *data_ptr = get_data_ptr_from_iter(&iter);
bpf_probe_read_user(event.dns_data, sizeof(event.dns_data), data_ptr);
```

**Особенности**:
- ✅ Простая обработка
- ✅ Данные всегда в одном месте
- ✅ Нет length prefix

#### TCP DNS

```c
// Сложная обработка - length prefix + фрагментация
u8 tcp_header[2];
bpf_probe_read_user(tcp_header, sizeof(tcp_header), data_ptr);
u16 dns_len = (tcp_header[0] << 8) | tcp_header[1];
bpf_probe_read_user(event.dns_data, dns_len, data_ptr + 2);
```

**Особенности**:
- ⚠️ Сложнее обработка
- ⚠️ Нужно обрабатывать length prefix (2 байта)
- ⚠️ Данные могут быть фрагментированы
- ⚠️ Может потребоваться kretprobe для надежности

### 4.3 Компромиссы

**Единый код для UDP/TCP?**
- ❌ Нет - слишком разные протоколы
- ✅ Раздельная обработка - проще и надежнее

**Fallback стратегия для TCP**:
```c
// Если не удалось прочитать с length prefix, пробуем без него
if (!data_read) {
    bpf_probe_read_user(event.dns_data, MAX_DNS_DATA, data_ptr);
}
```

**Обоснование**: Некоторые приложения могут отправлять DNS без length prefix.

## 5. Парсинг DNS заголовка

### 5.1 Проблема

Необходимо безопасно парсить DNS заголовок (12 байт) с учетом:
- Bounds checking (защита от переполнения)
- Валидация данных
- Извлечение ключевых полей

### 5.2 Принятое решение

```c
static __always_inline void parse_dns_header(u8 *data, u16 data_len, struct dns_event *event) {
    // BOUNDS CHECK: минимум 12 байт для заголовка
    if (!data || data_len < DNS_HEADER_SIZE) {
        event->dns_id = 0;
        event->dns_flags = 0;
        event->dns_questions = 0;
        event->dns_answers = 0;
        return;
    }
    
    event->dns_id = (data[0] << 8) | data[1];
    event->dns_flags = (data[2] << 8) | data[3];
    event->dns_questions = (data[4] << 8) | data[5];
    event->dns_answers = (data[6] << 8) | data[7];
}
```

### 5.3 Компромиссы

**Полный парсинг vs Минимальный**:

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| **Полный парсинг** | Больше информации | Больше кода, больше overhead |
| **Минимальный** ✅ | Достаточно для детекции | Меньше информации |

**Выбран минимальный парсинг**:
- Только критичные поля для детекции
- Полный парсинг в userspace (Python)

**Bounds checking**:
- ✅ Обязателен для безопасности
- ✅ Защита от переполнения буфера
- ✅ Graceful degradation при ошибках

## 6. Обработка фрагментированных данных (iov_iter)

### 6.1 Проблема

Данные в `iov_iter` могут быть:
- В одном буфере (`ubuf` - ядра 5.14+)
- В массиве буферов (`iov` - ядра 5.x)
- Фрагментированы между несколькими вызовами

### 6.2 Принятое решение

```c
static __always_inline void *get_data_ptr_from_iter(struct iov_iter *iter) {
    void *data_ptr = NULL;
    
    // Пробуем ubuf (ядра 5.14+, 6.x)
    bpf_probe_read_kernel(&data_ptr, sizeof(data_ptr), &iter->ubuf);
    
    if (!data_ptr) {
        // Fallback: iov (ядра 5.x и ранее)
        const struct iovec *iov = NULL;
        bpf_probe_read_kernel(&iov, sizeof(iov), &iter->__iov);
        if (iov) {
            bpf_probe_read_kernel(&data_ptr, sizeof(data_ptr), &iov->iov_base);
        }
    }
    
    return data_ptr;
}
```

### 6.3 Компромиссы

**Обработка фрагментации**:

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| **Только первый буфер** ✅ | Просто, работает в 99% случаев | Может пропустить данные в других буферах |
| **Обработка всех буферов** | Полная обработка | Сложно, больше overhead |

**Выбран подход "только первый буфер"**:
- В большинстве случаев DNS данные в первом буфере
- Сложность обработки всех буферов не оправдана
- Известное ограничение для `dig +tcp` (данные в нескольких вызовах)

**Известное ограничение**:
- ❌ `dig +tcp` может отправлять данные через несколько `sendmsg()` вызовов
- ✅ Прямой socket работает корректно (данные в одном вызове)

## 7. Контекстные Maps для kretprobe

### 7.1 Проблема

В kretprobe нет доступа к аргументам функции. Необходимо сохранять контекст между kprobe и kretprobe.

### 7.2 Принятое решение

```c
// Контекст для TCP sendmsg
struct send_context {
    void *data_ptr;
    struct msghdr *msg;  // Для повторного чтения в kretprobe
    u32 saddr;
    u32 daddr;
    u16 sport;
    u16 dport;
    u64 cgroup_id;
    u32 netns_id;
    u64 timestamp_ns;
    u32 pid;
    u32 tid;
    char comm[16];
};
BPF_HASH(send_ctx_map, u64, struct send_context, 10240);
```

**Использование**:
- kprobe: сохраняем контекст в map (ключ: `pid_tgid`)
- kretprobe: читаем контекст, удаляем из map

### 7.3 Компромиссы

**Размер map (10240 записей)**:

| Размер | Плюсы | Минусы |
|--------|-------|--------|
| 1024 | Меньше памяти | Может переполниться при высокой нагрузке |
| **10240** ✅ | Достаточно для большинства случаев | Больше памяти |
| 65536 | Очень большой | Избыточно |

**Обоснование 10240**:
- Типичная нагрузка: 100-1000 DNS запросов/сек
- kretprobe вызывается быстро (микросекунды)
- 10240 записей достаточно для burst

**Очистка map**:
- ✅ Обязательна в kretprobe (защита от утечек памяти)
- ✅ Используется `delete()` после чтения

## 8. Фильтрация в Kernel vs Userspace

### 8.1 Проблема

Где выполнять фильтрацию подозрительных DNS запросов:
- **Kernel space**: Быстрее, меньше данных в userspace
- **Userspace**: Гибче, проще разработка

### 8.2 Принятое решение: Userspace фильтрация

**Текущая версия (2.1)**: Все DNS события отправляются в userspace, фильтрация в Python.

**Обоснование**:
1. **Гибкость**: Легко изменить правила детекции
2. **Простота разработки**: Не нужно проходить eBPF verifier
3. **Реальная нагрузка низкая**: 1-10 подозрительных событий/сек
4. **Сложность kernel фильтрации**: Парсинг DNS доменов в eBPF сложен

### 8.3 Компромиссы

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| **Kernel фильтрация** | Быстрее, меньше данных | Сложно, ограничения verifier |
| **Userspace фильтрация** ✅ | Гибко, проще | Больше данных в userspace |

**Будущие улучшения**:
- Можно вернуться к kernel фильтрации для оптимизации
- Текущий подход достаточен для production

## 9. Идентификация Kubernetes Pods

### 9.1 Проблема

Необходимо идентифицировать источник DNS запроса в Kubernetes:
- Какой pod отправил запрос?
- В каком namespace?

### 9.2 Принятое решение

```c
// Идентификация пода
event.cgroup_id = bpf_get_current_cgroup_id();
event.netns_id = get_netns_id(sk);
```

**Методы идентификации**:

1. **cgroup_id**: ID cgroup процесса
   - Уникален для каждого pod
   - Доступен через `bpf_get_current_cgroup_id()`

2. **netns_id**: ID network namespace
   - Уникален для каждого pod (если используется отдельный netns)
   - Извлекается из `sock->__sk_common.skc_net.net->ns.inum`

3. **PID + comm**: Дополнительная информация
   - `pid` и `comm` для идентификации процесса

### 9.3 Компромиссы

**Методы идентификации**:

| Метод | Надежность | Overhead |
|-------|------------|----------|
| **cgroup_id** ✅ | Высокая | Низкий |
| **netns_id** ✅ | Средняя (зависит от конфигурации) | Низкий |
| **PID** | Низкая (может переиспользоваться) | Низкий |

**Ограничения**:
- ⚠️ `netns_id` может быть 0, если pod использует host network
- ✅ `cgroup_id` всегда доступен в Kubernetes

## 10. Timestamp для анализа частоты

### 10.1 Проблема

Для детекции C2 (Command & Control) необходимо анализировать частоту DNS запросов. Нужен точный timestamp из kernel.

### 10.2 Принятое решение

```c
event.timestamp_ns = bpf_ktime_get_ns();
```

**Использование**:
- `bpf_ktime_get_ns()` - monotonic time из kernel
- Наносекундная точность
- Используется в userspace для анализа частоты запросов

### 10.3 Компромиссы

**Monotonic vs Wall clock**:

| Тип | Плюсы | Минусы |
|-----|-------|--------|
| **Monotonic** ✅ | Не зависит от NTP, стабилен | Не соответствует реальному времени |
| **Wall clock** | Соответствует реальному времени | Может "прыгать" при NTP sync |

**Выбран monotonic**:
- Стабильность важнее соответствия реальному времени
- Анализ частоты не требует реального времени
- Защита от NTP корректировок

## 12. Известные ограничения

### 12.1 TCP через `dig +tcp`

**Проблема**: Данные не парсятся для `dig +tcp`

**Причина**: 
- `dig` отправляет TCP DNS данные через несколько вызовов `sendmsg()`
- Length prefix и DNS данные могут быть в разных вызовах
- eBPF перехватывает не тот вызов

**Решение**: 
- ✅ Прямой socket работает корректно
- ❌ `dig +tcp` - известное ограничение

### 12.2 TCP RESPONSE парсинг

**Проблема**: Многие TCP RESPONSE показывают `<unparseable>` (60%)

**Причина**:
- TCP RESPONSE может быть большим (до 64KB)
- Данные могут быть разбиты на несколько пакетов
- Length prefix может быть в отдельном пакете

**Статус**: 
- Частично работает (40% успешных)
- Проблема в основном с большими ответами

### 12.3 Фрагментированные данные в iov_iter

**Проблема**: Данные могут быть в нескольких буферах

**Решение**: 
- Обрабатываем только первый буфер
- Известное ограничение для сложных случаев

## 14. Заключение

Архитектурные решения в eBPF модуле балансируют между:
- **Производительностью**: Ring Buffer, минимальный парсинг
- **Надежностью**: Bounds checking, graceful degradation
- **Простотой**: Userspace фильтрация, обработка первого буфера
- **Современностью**: Ring Buffer, актуальные API

Все решения обоснованы реальными требованиями и компромиссами, характерными для eBPF разработки.
